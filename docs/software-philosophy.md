# 软件哲学规则

## 失败
1. 可以吞掉一个错误，但"吞"这个动作必须在代码和运行时都留下痕迹。三条缺一不可：
   - **窄**：指名你要容忍的那一个错误（`except KeyError`），不许兜底（`except:`、`catch (e) {}`、`|| true`、`2>/dev/null`）。兜底连你没预料到的错误一起吞了，而那些正是你需要看见的。
   - **有理由**：写下为什么这个错误可以不管。写不出理由，就是它不该被吞。
   - **可区分**：下游能分辨"正常的空"和"失败后的空"。降级返回默认值时，默认值必须携带降级标记，否则失败会伪装成正常数据继续往下走。
2. 判定该不该炸，只问一件事：这个输入是否存在唯一一个所有调用方都会选的答案。
   - 有（`sum([])` → `0`、越界切片取到结尾）：库直接给出，不许抛。抛了就是把复杂度推给调用方，同一段边界处理会散落到几十个调用点。
   - 没有（`max([])`、`int("abc")`、除零）：立即崩溃，不许猜。猜出来的值会一路流向下游。
   - fail-fast 针对的是**未定义**，不是**罕见**。别把规则 1 读成"边界情况一律抛异常"。
3. 恢复路径越少越好，最好只有重启一条——错误处理代码是测试覆盖最差的代码。
4. 系统永远部分带伤运行，防线不是不出错，是知道哪儿在带伤。

## 复杂度
5. 复杂度首要来源是状态，其次控制流，最后才是代码量。先砍状态。
6. 区分本质复杂度与偶然复杂度；任何新工具先问减的是哪种。
7. Simple 是结构不缠绕，easy 是你恰好熟悉。别拿后者冒充前者。
8. 模块价值 = 功能 ÷ 接口。薄包装是负资产。
9. 不按行数拆函数。每个切口都是新接口。
10. 复杂度默认只增不减；降复杂度是独立预算项，不排期等于不做。

## 边界
11. 模块边界藏易变的设计决策，不照执行流程切。
12. 功能放在掌握全部上下文的端点实现；底层重复做要么冗余要么错。
13. 实际行为就是契约，写下来的不是。不想被依赖的行为要主动随机化。
14. 配置用表达力最弱的够用语言。越弱越可分析。
15. 架构改不动时先看组织——系统长成沟通结构的形状。

## 时间
16. 代码是理论的有损投影；给下一个人留的是重建理论的线索，不是代码本身。
17. 技术债 = 代码与当前理解的落差，不是烂代码。理解加深后不改代码就是在付利息。
18. 先让改动变容易，再做那个容易的改动。
19. 概念连贯但功能少 > 各自不错但互不协调。
20. 看不出栅栏为什么在那儿之前，别拆。
21. 写代码用了全部聪明，就不剩聪明去调试它。

## 度量
22. 指标成为目标即失效。
23. 测试证明 bug 存在，不证明不存在；一百个相似用例 ≈ 一个。
24. 恢复路径只有故障注入能测。
25. 拒绝一个方案时写下预测（哪儿崩、多久崩），事后对账——被拒方案的后果是永久缺失的数据，不写就只剩越来越自信的错觉。

## 不继承
- Postel 宽容接收：静默失败的制度化。
- 函数长度上限：见规则 9。
- DRY 用于文本：原意是知识不重复。重复远比错误抽象便宜。
- SOLID 的 S 和 O：不可证伪 / 投机泛化邀请函。
- GoF 大半：语言缺陷的补丁。
- 微服务默认化：组织没拆先拆系统 = 分布式单体。

## 元规则
26. 教条失效的方式都一样：结论流传，前提丢失。引用前读原文。
