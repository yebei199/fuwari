## 场景

一台安卓平板通过无线调试挂在 A 机的局域网里(`手机内网IP:5555`),而我人坐在 B 机前。
两台机器不在同一个二层网络,B 机只能通过 VPN 访问到 A 机,**够不到那个内网地址**。

目标很简单:在 B 机上看到平板屏幕并用鼠标键盘操作它。

## 方案:一条 ssh 反向隧道

从 A 机发起,把手机的 adb 端口反向转发到 B 机:

```bash
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
    -R 15555:<手机内网IP>:5555 <B机>
```

然后在 B 机上:

```bash
adb connect 127.0.0.1:15555
scrcpy -s 127.0.0.1:15555
```

用 `-R` 而不是 `-L`,是因为**能看到手机的那一端是 A 机**。转发的目标地址在 ssh 客户端侧解析,
所以隧道必须从 A 机建立。反过来在 B 机上写 `-L` 是行不通的,B 机根本解析不到那个内网地址。

`ExitOnForwardFailure=yes` 值得加:端口被占用时让 ssh 直接失败退出,而不是傻站着一个
没有转发的连接——否则你会对着一个"看起来连着"的隧道排查半天。

## 坑一:`adb connect` 是独立且必须的一步

隧道通了不等于 adb 连上了。这两件事经常被混为一谈。

**scrcpy 自己不发起网络 adb 连接。** 它只是向本机的 adb server 索要设备列表,拿不到就报:

```
ERROR: Could not find any ADB device
ERROR: Server connection failed
```

网络 adb 不像 USB——USB 插上会被 adb server 自动发现,TCP 模式必须显式 `adb connect` 一次。

还有一个更隐蔽的变体:**隧道被硬断之后,B 机的 adb server 里会留一条 `offline` 的僵尸条目**。
这种状态下重建隧道也不会自动恢复,scrcpy 照样报"找不到设备"。重新 `adb connect` 才能刷掉它。

排查时先看这个,别急着怀疑隧道:

```bash
adb devices -l    # 要看到 device,不是 offline,也不是空列表
```

## 坑二:默认参数会把设备烤热

这是最反直觉的一个。第一次连上用了一阵子后,平板烫得不正常。

我一开始怀疑是屏幕常亮(为了投屏方便开了 `svc power stayon true`),但这个解释站不住:
平时正常玩游戏也是常亮,并没有这么烫;而且**一关掉 scrcpy 就恢复正常**。

真正的原因是 **scrcpy 打满了设备的硬件视频编码器**,而这是日常使用完全不会触发的一路负载。

三个因素叠加:

1. **scrcpy 默认跟随屏幕刷新率、不限帧。** 这台平板的屏支持到 185Hz:

   ```
   supportedRefreshRates [60, 90, 120, 144, 165, 185]
   ```

   于是 scrcpy 尝试以最高 185fps 编码。
2. **默认按屏幕原生分辨率编码。** 实测虚拟显示器是 `2400 x 1504`。
3. **默认码率 8Mbps。**

关键区别在这里:**玩游戏用的是 GPU,不碰视频编码器。** 而 scrcpy 是在既有负载之上,
额外把 SoC 的媒体编码模块长期钉死。所以"常亮玩游戏不烫、一开投屏就烫、一关就好"这个现象
完全对得上——它们根本不是同一个发热源。

### 解法:三个限流参数

```bash
scrcpy -s 127.0.0.1:15555 \
  --no-audio --max-fps=30 --max-size=1280 --video-bit-rate=4M
```

限流前后实测对比:

| 项目 | 默认 | 限流后 |
|------|------|--------|
| 虚拟显示器分辨率 | 2400 × 1504 | 1280 × 802 |
| 帧率上限 | 跟随 185Hz | 30 |
| 码率 | 8 Mbps | 4 Mbps |

像素量降到约 1/3.5,帧率降到约 1/6,合起来编码负载是原来的十分之一量级。

打字、点按钮这类操作,30fps + 1280 完全够用,画面照样清楚。
**如果要更流畅可以把帧率提到 60,但不要动 `--max-size`——分辨率才是编码负载的大头。**

## 坑三:投屏会把声音从扬声器偷走

同一次连接里还出现了"手机突然没声音"。

原因是 **scrcpy 2.x 起默认转发设备音频**,它通过 `REMOTE_SUBMIX` 抓取音频流。
在部分机型上这个抓取是**独占**的:声音被整个重定向到电脑,手机扬声器彻底哑掉。

验证方式是看当前音频输出设备:

```bash
adb shell "dumpsys audio | grep -m2 'Devices:'"
```

被抓走时能看到 `remote_submix` 相关的路由;正常时应该是:

```
Devices: speaker(2)
```

`--no-audio` 一次解决两个问题:声音回到扬声器,同时省掉一路编码开销。

## 坑四:登录页一律黑屏,但不是卡死

真正开始用之后必然会撞上的问题:**很多应用的登录页在投屏里是纯黑的。**

这是 `FLAG_SECURE` 窗口标记,系统级的防截屏机制。截屏和投屏都会拿到黑屏,
**但手机本机屏幕上显示完全正常**。确认方法:

```bash
adb shell "dumpsys window windows" | grep -A12 "<目标Activity>" | grep "fl="
# 出现 SECURE 就是它
```

涉及手机号、验证码、密码的页面基本都会加这个标记。这不是故障,是设计。

### 绕法:`uiautomator` 不受 `FLAG_SECURE` 限制

有意思的是,**控件树导出不受这个标记影响**。看不见画面,但能读到完整的控件结构和坐标:

```bash
adb shell uiautomator dump /data/local/tmp/ui.xml
adb pull /data/local/tmp/ui.xml
```

解析出每个控件的 `text`、`resource-id`、`bounds`,就能精确计算点击坐标。
"看不见但能操作"在这种场景下是可行的。

需要注意的例外:**个别应用会专门反自动化。** 遇到过某个授权页导出的控件树只有一个
`bounds="[0,0][0,0]"` 的空节点——这种就只能上手机本机操作了。

### 附带发现:协议勾选框

用控件树排查时发现一个普遍问题:很多登录页底部的"我已阅读并同意《用户协议》"
**默认是未勾选的**,而且不勾的话点登录**没有任何反馈**——不弹提示、不报错、界面完全不动。

配合黑屏,这个组合极具迷惑性:你以为页面卡死了,实际上它在安静地等你勾一个看不见的框。

```bash
# 直接查勾选状态,比盲点靠谱
adb shell "cat /data/local/tmp/ui.xml" | grep -o 'checkbox[^>]*checked="[a-z]*"'
```

## 三条自查命令

连上之后先跑这三条,确认限流真的生效了,别等发烫才发现:

```bash
# 1. 虚拟显示器分辨率,验证 --max-size 生效
adb shell "dumpsys display | grep -o 'DisplayInfo{\"scrcpy\"[^}]*real [0-9 x]*'"

# 2. 温度,mStatus=0 表示未触发降频
adb shell "dumpsys thermalservice | grep -E 'battery|GPU0'"

# 3. 音频输出设备,应该是 speaker
adb shell "dumpsys audio | grep -m2 'Devices:'"
```

关于温度读数有个提醒:这台设备的 `dumpsys thermalservice` 里,八个 CPU 核心报的是
完全相同的 `99.6`,这基本可以确定是**未实现的传感器占位值**,不能当真。
可信的是电池和 GPU 的读数,以及 `mStatus`——真到 99.6°C 早就重度限频了。

## 什么时候不该用这套

- **同一局域网内不需要隧道。** 直接 `adb connect <手机IP>:5555` 就行,加一层 ssh 纯属自找麻烦。
- **要看游戏实时操作时,限流参数会碍事。** 30fps 看不出连招细节。这种情况老实提高帧率,
  并接受发热,或者干脆用设备自带的录屏事后回看。
- **需要在防截屏页面里做视觉判断时。** 控件树能给你结构,给不了渲染效果。
  要确认 UI 长什么样,只能看本机屏幕。

## 小结

跨机器投屏本身只是一条 `ssh -R`,真正花时间的是三个默认行为:
**不限帧编码**烤设备、**默认抓音频**偷声音、**`adb connect` 必须显式执行**。

前两个的共同点是 scrcpy 的默认值面向"局域网内、追求最佳体验"这个场景,
而跨机器远程操作的诉求完全不同——够看就行,别把设备当编码机用。
