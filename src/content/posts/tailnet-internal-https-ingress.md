这件事的起点是一句话：**「当前 headscale 私有网络之间都是 http，没有 https，这不安全，怎么解决？」**

最后确实上了一套 Caddy 反代 + 通配证书，内网服务都有了锁头。但整个过程里，值得写下来的几乎没有一样和证书有关。

## 前提是错的

先说结论：**tailnet 里的 http 不是明文。**

WireGuard 已经对每一跳做了端到端加密、双向认证和前向保密，密钥由 headscale 分发。`http://100.64.x.x:3000` 这个 URL 的 scheme 是 http，但包在线路上不是明文。在它上面再套一层 TLS，是加密两次。

所以「不安全」这个判断不成立。那真实诉求是什么？把选项摊开问了一轮，答案是：**打开管理页时地址栏别显示「不安全」。**

这是个 UX 问题，不是安全问题。而这个区分决定了后面所有取舍：

- 如果目标是加密，方案得覆盖所有流量；
- 如果目标是浏览器提示，方案只需覆盖**浏览器实际打开的、且没有 https 的**那几个。

一个字之差，工程量差一个数量级。

**第一条可复用的结论：先问「这加密的是什么」。** 有人说「都是 http，不安全」时，先确认底层链路是不是已经加密了。VPN、service mesh、WireGuard、同机回环——这些场景里的 http 都不是明文，在上面加 TLS 是花钱买安慰。

## 范围清点：清单塌了一大半

确认了目标是「消除浏览器警告」，就得清点：哪些服务是浏览器打开的、且真的没有 https？

主机上跑着二十来个服务。清点结果出乎意料地小：

| 服务 | 现状 |
| --- | --- |
| grafana、authentik、forgejo、affine、lemmy、vaultwarden…… | 早就有 https——它们都挂在 Cloudflare tunnel 后面 |
| VictoriaMetrics、ClickHouse | 走 SSH 端口转发到 `127.0.0.1`——**localhost 本身就是 secure context**，浏览器不报警告 |
| headplane、LLM 网关调试台、对象存储 console | 🔓 真的裸着 |

**真实范围是 3 个偶尔打开的后台。**

第二行值得单独说：按 W3C 规范，`http://localhost` 和 `http://127.0.0.1` 是 potentially trustworthy origin，**是 secure context**。WebCrypto、剪贴板、Service Worker 都能用，浏览器也不弹警告。所以「SSH 转发到 localhost」本身就是一个完整的解法，零组件、零证书。

我在清点时犯了个错，值得记下来：第一版清单是 grep 部署代码得出的，漏掉了「手工配在隧道里、只记在 README 的映射」，于是把两个早就有 https 的服务（其中一个是密码管理器）算成了裸奔，还拿它当过「必须做」的最强论据。**清单的来源单一，结论就不可信。** 后来用 README 交叉验证，那个最强论据当场消失。

## 明知不划算，还是做了

为 3 个一个月开不了几次的后台建反代 + 通配证书 + 自建镜像，单看收益是不成立的。更省事的路有两条，而且仓库里都有先例：SSH 转发到 localhost；或者接进现有的 Cloudflare tunnel + Access。

最后还是做了，理由是**能力，不是这 3 个服务**——想要一个「内网服务不绕 Cloudflare 就能有 https」的标准入口，以后加服务只需要改一行路由表。

这个决定被明确写进设计文档，连同一条自毁条款：

> 如果半年后这个子域下仍然只有这 3 个服务，那这个决定就是错的，应该拆掉。

记录它是为了让将来的读者知道：这不是有人误判了工作量，是明知不划算而为了能力买的单。

有意思的是，做这个决定的**当天**，替代方案之一被实测否决了。对象存储的 console 原本挂在公网隧道后面，那天被撤了下来——原因不是安全，是**它在公网上根本干不了活**：Cloudflare 的代理层会把空 body 的 PUT 转成 chunked 编码、丢掉 `Content-Length`，而后端硬性要求这个头，于是建桶按钮必然 411。

**把内网后台塞进 CDN 隧道，等于让它参与改写你的每一个请求。什么时候踩到，取决于那个应用的协议细节，踩到之前没有任何征兆。** 那条替代方案从「先例」变成了「论据」。

## 子域选择：最顺手的那个是最差的

最初的提议是直接用 MagicDNS 的 `base_domain`（`tail.cryptorust.uk`）。**它恰好是最差的选择。**

那个子域归 headscale 的 DNS 管，而 MagicDNS **只认节点名**：

- `accept-dns=true` 的节点：查 MagicDNS → `grafana.tail.cryptorust.uk` → NXDOMAIN；
- `accept-dns=false` 的节点：查公共 DNS → 走 Cloudflare → 能解析。

**同一个域名在不同节点上结果不同**，是最难排查的那类故障。而恰好那台服务器自己跑的就是 `--accept-dns=false`。

要修就得给每个服务往 headscale 的 `extra_records` 里加一条，于是路由表存在两处（反代配置 + headscale 配置），加服务要改两处并重启控制面。

换一个 MagicDNS 不碰的新子域，这些全部消失，而且**一条通配 A 记录管一辈子**：

```
*.svc.cryptorust.uk  A  <tailnet IP>   (DNS-only，灰云)
```

证书也是一张通配。加服务只动反代配置，不碰 DNS、不碰证书。

## 443 冲突：选了更丑但能被验证的那个

443 被 headscale 独占，而且它必须在 443——那是它的公网入口，没得挪。

考虑过让 Caddy 占 443、按 Host 头把 headscale 转发到后面。URL 最干净。**否决它的理由是：现有的监控看不见它。**

背景：这套基础设施里有一个从外部视角核对端口暴露面的检查，偏离基线就告警。它的整个前提是 **「暴露面 = 端口」**。

如果让 Caddy 占 443，那内网后台是否对公网暴露，就不再取决于端口，而取决于 Caddy 配置里那条 `remote_ip` 规则写没写对——而 443 本来就在允许公网开放的白名单里，**那个检查永远不会报警**。写错一个字符，内网后台对全世界敞开，而唯一的监控系统报告一切正常。

所以选了另起一个端口，和其余服务同一个模型，再把它加进被核对的清单——**那个检查就自动成为「反代没被公网够到」的持续验证**。

代价是 URL 里多个 `:8443`，丑。但端口号不影响 TLS：锁头照有，secure context 照样成立。

**第二条可复用的结论：一道无法验证的防线，比没有防线更糟。** 它让你以为自己被保护着。宁可选一个更丑、但现有监控能看见的方案。

## 想用 Rust 反代，最后用了 Caddy

中途提了个需求：想用 Rust 写的反代，「比如 CF 开源的那个」。查完的结论：

| 方案 | 状态 |
| --- | --- |
| **Pingora** | 是**库**不是程序。无配置文件、无二进制、**无任何 ACME**。要用得自己实现 `ProxyHttp` trait 并自接证书 |
| **River**（Pingora 上的成品反代） | v0.5.0 / 2024-08，官方声明 *"Development is currently paused"*、*"no expectation of stability"*。停更近两年 |
| **rpxy** | ACME 只支持 TLS-ALPN-01 → **签不了通配证书**（Let's Encrypt 通配只认 DNS-01），且需要 443 入站。双重不可行 |
| **Pingap** | Pingora 上的成品反代，活跃，HTTP-01 + DNS-01 齐全。**唯一可行的 Rust 选项** |

Pingap 技术上成立，但 pre-1.0、基本单人维护、README 明示「稳定前不接受 PR」，而它要挡在内网后台前面并持有签证书用的 API 令牌。

摊开风险之后，需求提出者自己改了主意，选了无聊但久经考验的 Caddy。**「Pingora」这个名字在很多人脑子里是「Cloudflare 的高性能反代」，但它其实是个需要你写 Rust 的库**——这个认知差本身就值得记一笔。

## 落地才知道的三个坑

前面全是纸上推理。真部署下去，三个坑一个没躲过。

### `localhost` 是错的

反代跑在容器里，`localhost` 指向容器自己，不是宿主机。这个大家都知道。但更有意思的是**三个后端的地址不对称**：

- headplane → 宿主机的 **tailnet IP**
- 另外两个 → `host.docker.internal`

不是笔误。headplane 只发布在 tailnet IP 上——**它的暴露面不依赖任何外部防火墙是否还站着**，这是它比同机其它服务更强的一点。

中途有个提议：把它改成 `0.0.0.0`，好让反代统一用 `localhost`。**否决**——那是把 headscale 的管理控制台从「自己就安全」降到「靠别人的墙才安全」，只为省几个字符。反代直接打 tailnet IP 就行，实测通。

**配置里的不一致有时是在如实反映现实。抹平它之前先问问它在反映什么。**

### 健康检查追不上首次签发

部署失败了，报 `TLS connect error: tlsv1 alert internal error`。

看日志：证书**签发成功了**。失败的是健康检查。

原因：部署框架的 `http_probe` 是**连续 5 次瞬间重试、中间不 sleep**，几秒就打完。而首次签发要走完 ACME 挑战 + 一轮 60 秒退避重试，实测约 **98 秒**。

**这个探测和签发赛跑，必输。任何首次部署都会假失败。**

改成了「等待循环 + 断言」：先轮询到通为止，再断言。这个坑不只影响反代——**任何启动需要几十秒的新服务都会中招**。

### ACME 孤儿记录：日志骗了我

第一次部署的日志里有一串 error：

```
cleaning up solver: no memory of presenting a DNS record for "_acme-challenge.svc..."
adding temporary record: HTTP 400: An identical record already exists
```

机制是这样的：容器在挑战途中被 compose 重建（SIGTERM），Caddy 的清理逻辑在内存里，重启后「不记得」自己放过那条 TXT；而 Let's Encrypt 对同一账户+域名**复用同一个 challenge token**，于是新容器算出的值和残留的一模一样，Cloudflare 返回 `81058 An identical record already exists`。

我当时的判断是「记录在累积，永远不会自愈」，然后手动停容器、清记录、重启。

**这个判断是错的。** 后来对时间戳才发现：Caddy 第二次重试就自己成功了，**在我清理之前**。certmagic 本来就是设计成会退避重试的，下一轮换新 order 就绕开了。我那次手动干预完全多余。

**日志里的 error 不等于终态。** 一个会自动重试的系统，中间过程必然刷 error；判断它是不是真的卡住，要看时间线，不是看有没有红字。

## 最大的坑在最后一跳

部署完，服务端我从两个位置用 curl 验通了：主机自己打自己，以及另一台 tailnet 节点。证书 `ssl_verify_result=0`，三条路由全绿。

然后浏览器打不开。

原因：**代理。**

`headplane.svc.cryptorust.uk` 是个货真价实的公网域名——`.uk` 顶级域、Cloudflare 托管、公网 DNS 查得到。本地代理（sing-box）的规则表里它一条都不匹配，于是落到默认的代理出站。而代理出口在另一台机器上，那台机器不在 tailnet 里，去连 CGNAT 地址自然连不到。

实测：走代理 `HTTP 000`，不走代理 `HTTP 200`。

最气人的是——**规则表里早就有一条 `ip_cidr = 100.64.0.0/10 → direct`**。它救不了：

> **sing-box 对域名请求是先按域名判路由、再解析。** 域名阶段就已经把连接送进代理出站了，IP 规则根本没机会匹配。

以前访问这些服务用的是 `<tailnet IP>:13000`——一个 **IP**，规则对私有网段直连放行，所以从没暴露这个问题。

**第三条、也是最重要的一条可复用结论：**

> 从「用 IP 访问」改成「用域名访问」，会改变**代理、DNS、防火墙、分流规则**对同一个目标的判断——因为这些东西大多在**域名阶段**决策，而域名不携带「我其实指向内网」这个信息。

设计文档里我把子域方案的代价写成了「不在 tailnet 时会连接超时」。漏了更常见的那半句：**在 tailnet 里、但开着代理时也会超时**。而那是日常状态。

整个 ADR 权衡的全是 DNS 解析层面的事，完全没考虑「**解析对了之后，包会不会被送错地方**」。

修法是在代理规则里给这个子域加显式直连。以后往这个子域下加服务不用再管（后缀是通配的），但**换代理方案、换客户端、加新机器时会重新踩**，因为那条规则在另一个仓库里。

## 顺带澄清一个常见误解

过程中被问了两次，值得单独写：

> 「后端那一段还是 http，浏览器不还是认为不安全吗？」

不会。**浏览器根本看不见那一段。**

TLS 终结的含义是**两条连接**：浏览器 ══https══> 反代 ──http──> 后端。浏览器发的请求到反代就结束了，反代解密之后**另起一条全新的连接**去打后端。锁头只反映浏览器到反代那一段。

这不是理论——**你所有的 https 服务现在就是这么跑的**。Cloudflare tunnel 的 ingress 全都是 `http://localhost:<port>`，锁头照样有。区别只是 TLS 在哪终结：CDN 那些是在**别人的机器上**解开明文，自建反代是在**你自己的机器上**。后者明文经过的地方更少。

至于反代到后端那一小段——它不出这台机器。要嗅探它得先拿到 root，而到那一步，所有服务的明文、数据库、密钥全在攻击者手里了，那段 http 是最不值得担心的东西。

## 最后

值得带走的：

1. **先问「这加密的是什么」**——已加密链路上再套 TLS 是花钱买安慰。
2. **清单来源单一，结论就不可信**——我拿两个早就有 https 的服务当过论据。
3. **无法验证的防线比没有防线更糟**——宁可丑一点，选现有监控能看见的。
4. **配置里的不一致，有时是在如实反映现实**——抹平之前先问它在反映什么。
5. **日志里的 error 不等于终态**——会重试的系统中间必然刷红字，看时间线。
6. **解析对了 ≠ 包会送对地方**——域名/IP 之别会改变整条链路上所有按域名决策的东西。

以及一个元结论：这次真正花时间的，没有一样是「怎么配 Caddy」。是「到底要解决什么」「范围有多大」「哪条防线能被验证」「最后一跳会不会被别人劫走」。**证书是这件事里最简单的部分。**
