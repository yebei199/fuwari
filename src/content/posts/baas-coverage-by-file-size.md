看到 TrailBase 的时候，第一反应是「这玩意儿能省我不少事」。

它的卖点很诱人：一个 Rust 写的单文件二进制，内嵌 SQLite，扔上服务器就是一整套后端——按表自动生成类型安全的 REST 接口、实时订阅、认证系统、Admin UI，自定义逻辑走 Wasmtime 跑 WASM。号称亚毫秒延迟。相当于自托管版的 Firebase，但不用把数据交给 Google，也不用像 Supabase 那样拉十几个容器。

于是问题来了：我手上那个跨端应用的仓库，该不该把后端换成它？

答案是不该。但比答案更有用的是**算出这个答案的方法**——它比读功能对比表快得多，而且不会骗人。

## 功能表是个陷阱

评估这类工具，最自然的做法是打开它的 feature list，一条条对照自己的需求打钩。认证 ✓、CRUD ✓、实时推送 ✓、权限控制 ✓、Admin 后台 ✓。五个钩打完，结论似乎是「完美契合」。

这个方法的问题在于，**功能表列的是它能做什么，不是你需要什么**。而且它天然偏向乐观：每一条你都能想出「这个我好像也用得上」，但没有任何一条会告诉你「你还有一半的活儿它接不了」。

更麻烦的是，功能表把所有条目摆得一样大。「用户认证」和「实时订阅」在表里各占一行，但在你的项目里，前者可能是 40 行代码，后者可能压根不需要。

换个问法就清楚了：**它能盖住我哪几个文件？**

## 把源码按体积排序

我那个仓库的后端是个 axum 服务，跑 `ls -S` 看一眼：

```
main.rs      43K
bangdream.rs 40K
cache.rs     11K
signaling.rs 10K
playlist.rs   8K
account.rs    8K
error.rs      7K
roster.rs     5K
history.rs    2K
auth.rs     1.5K
db.rs       0.9K
lib.rs      0.6K
```

再逐个问「TrailBase 能替掉它吗」：

| 文件 | 干什么的 | 能替吗 |
|---|---|---|
| `bangdream.rs` 40K | 把上游一个私有 gRPC 服务翻译成 HTTP/JSON | ❌ 它不认识我的上游 |
| `main.rs` 43K | 路由装配、启动、依赖注入 | ❌ 装配的是上面这些东西 |
| `cache.rs` 11K | 平台数据缓存，有自己的失效策略 | ❌ 业务逻辑 |
| `signaling.rs` 10K | WebRTC 同播的 WebSocket 信令 | ❌ 它不是信令服务器 |
| `account.rs` + `auth.rs` 9.5K | 注册登录、argon2、session token | ✅ |
| `playlist.rs` + `history.rs` 10K | 歌单和播放事件的 CRUD | ✅ |

字节数不等于复杂度，但作为「这块活儿有多少」的粗略代理，它够用了，而且不需要我重新读一遍自己的代码。结果是 **61% 的体积它碰不到，14% 能换掉**（剩下的是 `error.rs`、`db.rs` 这类基础设施，跟着走）。

这个比例是整个决策的全部内容。功能表上五个钩，落到实处只盖住了七分之一。

## 14% 换来什么

诚实地说，好处是真的：

**删代码**。注册、登录、密码哈希、session token 落库和校验，加上歌单/播放事件的增删改查，连同五条 migration（`0001_accounts`、`0002_local_playlists`、`0003_play_events`……）一起消失，改成在管理界面里点几下建表。

**白送一个 Admin UI**。这个是纯赚的。现在想看某个账号下的歌单，得 SSH 上去开 psql。自己写一个后台要好几天，而且写完还得维护。

**少一个容器**。SQLite 单文件替掉 Postgres，compose 里少一个服务、少一份备份策略。对同时在维护基础设施仓库的人来说，这条的价值比看起来大。

**权限从代码变成配置**。「只有本人能读自己的歌单」现在是 Rust 里的一个 if，以后是一条 SQL 表达式，改了不用重新编译部署。

四条都不是空话。如果这是个新项目，它们加起来足够让我直接上。

## 但是「两个后端」

那 61% 必须留在原来的 axum 服务里——gRPC 翻译层和 WebSocket 信令，TrailBase 一个都接不了。

所以引进它的结果不是「换掉后端」，是**多一个后端**。客户端要同时跟两个地方说话：业务数据走 TrailBase 的接口，上游聚合和信令走自己的 axum。

代价不只是多一个进程。我那个仓库里有个 `contract` crate，客户端和服务端共享同一套类型定义，依赖方向严格单向（`apps/* → ui → app-core → api → contract`）。TrailBase 自动生成的接口不在这套类型体系里，于是共享类型只能盖住一半，另一半得写胶水缝起来。

**一个自动生成的接口，代价是它生成的类型不归你管。** 单后端的项目里这不是问题，双后端里它就是一条断层。

净收益：删掉大约 20K 已经写完、有测试盖着、跑得好好的代码，换来一个新进程和一层类型断层。不划算。

## 真正的锁定不在数据

聊到「以后项目变大了再换掉」这个假设时，还有一层容易搞反的东西。

大多数人担心的是数据被绑架。这个担心对 Firebase 成立——私有格式、私有协议，想走等于重写。但对 TrailBase 这类自托管的东西基本不成立：底下就是 SQLite 或 Postgres，`pg_dump` 一下或者直接拷文件就走了。

**真正粘住你的是客户端。**

一旦业务代码里到处写着 `trailbase.records("playlists").list(...)`，这个 SDK 的形状就渗进了整个前端。换后端等于每个调用点都要改，而调用点的数量随时间线性增长——写得越久越换不动，跟数据量一点关系都没有。

对策便宜到不像话：中间隔一层自己的函数。

```rust
// 而不是让整个 UI 层直接认识 BaaS 的 SDK
pub async fn fetch_playlists(user: UserId) -> Result<Vec<Playlist>>
```

这层薄得几乎没有内容，但它就是「以后能换」和「以后换不动」的分界线。有意思的是，`contract` + `api` 这种分层本来就在干这件事——为别的理由（跨端复用、依赖方向）做的设计，顺带把这个坑填了。

## 结论和适用边界

**判断方法**：想知道一个 BaaS 值不值得引进已有项目，别读功能表，去数你的后端源码。它能盖住的比例决定一切。超过一半，认真考虑；只有一两成，那是在给自己加一个进程。

**新项目另说**。这套算法算的是「省下已经写完的代码」，那当然不划算。新项目里同样这四条好处省的是**还没写的代码**，性质完全不同。只需要「用户能登录 + 存点数据」的时候，它是个好选择。

**几个具体的注意点**：TrailBase 目前挂着 Alpha 标签；server 用 OSL-3.0（copyleft，作为独立进程调用不传染，但商用前值得看一眼），客户端库是 Apache-2.0；Postgres 支持从 v0.28 起还是实验性的，默认路径是内嵌 SQLite。

**这套方法不适用的场景**：如果后端本身就是薄薄一层 CRUD 加认证——那种「61%」根本不存在的项目——直接算比例会得出「全都能替」，那时候要评估的就不是覆盖率而是别的东西了（成熟度、锁定、运维）。覆盖率高只是必要条件。
