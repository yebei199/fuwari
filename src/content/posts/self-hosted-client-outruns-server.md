一句话报障：**「我的 vault 应用没反应，是服务器出问题了吗？」**

最后的结论是服务器一直好好的，问题在客户端和服务端的版本差上。但更值得写的是中间那段——因为「服务器出问题了吗」这个问句本身，会把排查引向错误的方向，而它引错的方式很典型。

## 三个症状，信息量差别巨大

初始信息只有「没反应」。多问了两轮之后，症状变成三条：

- 手机 App：能看，一切正常
- 浏览器打开 web vault：能登录，能用
- 浏览器插件：能登录，能进主界面，但密码列表**永远停在骨架屏**（那种灰色占位条一直在闪）

这三条摆在一起，服务端故障的可能性基本就没了。理由不在于「有客户端能用」，而在于**插件本身登录成功了**。

登录成功意味着这条链路全通：DNS → Cloudflare Tunnel → 容器 → `/identity/connect/token` → 数据库。一个宕掉的服务端做不到登录成功之后再单独让列表渲染失败。所以故障点在登录之后、渲染之前——要么是同步请求，要么是客户端拿到数据后的处理。

顺手做的排除性验证，两条 curl：

```bash
curl -o /dev/null -w '%{http_code}' https://<vault域名>/alive
curl https://<vault域名>/api/config
```

都是 200。而且这两条是在**报障的那台机器上**跑的——这一点很关键，它同时排除了「这台机器的网络到不了服务端」这个假设。如果只在服务器本地测，就证明不了这件事。

## 决定性证据在一个不起眼的端点

Bitwarden 生态里，`/api/config` 是免鉴权的，返回里有一行：

```json
{ "version": "2025.12.0", "gitHash": "f21a3ada" }
```

这个 `version` 不是 vaultwarden 自己的版本号（当时是 1.36.0），而是它**声称兼容的 Bitwarden 客户端 API 版本**。

这就是答案。浏览器插件由浏览器商店自动更新，早就跑到了 2026 年的版本；服务端还停在 2025.12 的 API 契约上。新客户端按新契约渲染，拿不到它期待的字段，于是登录、同步这些老接口都成功，只有列表渲染卡死——正好就是那个骨架屏。

而手机 App 之所以「还能看」，有两层原因：移动端商店的更新推送慢一步，加上本地已经有解密好的缓存库。**它的「正常」是过期数据造成的假象，不是证据。**这一点差点误导整个判断：一开始「手机能看」被当成了「服务端没问题」的佐证，但它实际上什么都不能证明。

## 自托管把版本关系倒过来了

用 SaaS 的时候，这类问题不存在。官方的服务端总是先于或同步于客户端发布，兼容性由厂商保证，用户永远不会遇到「客户端比服务端新」。

自托管把这个关系**反了过来**：

- 客户端（浏览器插件、手机 App）走公共分发渠道，**自动更新，你管不着**
- 服务端在你自己的机器上，**手动更新，你不动它就不动**

于是随着时间推移，客户端只会越来越新，服务端只会越来越旧，差距单调扩大。这不是偶发故障，是一个**必然会发生、只是不知道哪天发生**的结构性问题。而且它触发的时机完全由第三方决定——浏览器商店什么时候推那个版本，你无从预知。

任何「兼容层协议 + 客户端不由你控制」的自托管服务都有这个问题，不只是 Vaultwarden。凡是你在用一个开源服务端 + 官方客户端的组合，都在这条线上。

## 修复：先备份，再动

诊断花了十几分钟，修复的动作本身很小——镜像 tag 从 `1.36.0` 换到 `1.37.1`（当时的最新版，四天前发布），重新部署。

但顺序不能反。密码库这种东西，升级前必须有一份能回去的快照。仓库里已经有现成的备份编排，跑出来的远端脚本是这样的：

```bash
docker stop vaultwarden
trap 'docker start vaultwarden >/dev/null' EXIT
docker exec postgres pg_dump -U "$PG_SUPERUSER" --clean --if-exists vaultwarden > "$backup_dir/vaultwarden.sql"
docker run --rm -v <数据卷>:/from:ro -v "$backup_dir":/to alpine:3.22 tar -C /from -czf /to/<卷名>.tar.gz .
docker start vaultwarden
trap - EXIT
restic backup ... --tag app:vaultwarden
```

有两个细节值得单独说：

**一是先停容器再 dump。** 密码库不像日志表，热备份拿到的可能是一个 postgres 和数据卷不一致的中间态。停几十秒换一份确定能还原的快照，这个交换很划算。

**二是那个 `trap`。** `trap 'docker start vaultwarden' EXIT` 保证脚本中途挂掉时容器也会被拉起来。没有它，一次 `pg_dump` 失败就等于服务永久停机直到有人发现。备份脚本自己把服务留在停机状态，是比备份失败更糟的结果。

## 验证要看运行事实，不是纸面事实

改完 tag、部署完，怎么算「升级成功」？

不能只看 compose 文件里的版本号变了——那只证明你改了文件。也不能只看 `docker ps` 里容器在跑——它可能跑的还是旧镜像，或者新镜像起来了但迁移失败。

真正的判据还是那个端点：

```
部署前：version: 2025.12.0   gitHash: f21a3ada
部署后：version: 2026.6.0    gitHash: 2629bcbe
```

`version` 变了，说明**正在响应请求的那个进程**确实是新二进制。这是运行事实，不是配置事实。这类判据的价值在于它无法被「改了文件但没生效」这种情况伪造。

几小时后又复查了一遍——版本号没变回去，说明没有崩溃回滚或者重启循环。这一步不是多余的：容器 `restart: unless-stopped` 的情况下，一个启动即崩的新版本会表现为「刚部署时正常，过一会儿全挂」。只在部署完那一刻验证，抓不到这种。

## 真正的教训：工具存在不等于工具在跑

这次事故的根因不是技术上的难点。仓库里**早就有**一个 `ops image check` 命令，它按一份镜像清单（记着每个镜像的当前 pin 和 tag 正则）去比对上游最新 tag。跑一次就能发现 vaultwarden 落后了。

问题是它没有被定期执行。没有排期，没有告警，等着人想起来手动跑。于是 1.37.1 发布之后在那儿躺了四天，直到浏览器插件先一步更新，用故障的形式把这件事通知了我。

这是一个很常见的模式：**能力已经建好了，但没有接到触发器上。**写工具的时候觉得「有需要就跑一下」，实际上「有需要」这个信号永远是事后才出现的——而事后就是故障。

对自托管来说，这条尤其硬：因为客户端不由你控制，服务端的更新滞后是有 deadline 的，只是那个 deadline 写在别人的发布计划里。

## 什么情况下这套判断不适用

- **客户端和服务端都由你分发**（比如自研前后端）：不存在这个倒置，反而是服务端容易跑在前面。
- **服务端有主版本跨越**：这次是 1.36 → 1.37，一个小版本，DB 迁移风险低。如果要跨大版本，得先看 changelog 里的 breaking change，逐版本升——之前踩过 Authentik 跳版本导致迁移死锁的坑，那种情况下「直接升到最新」是错的。
- **症状是彻底打不开而非部分功能失效**：那才该往服务端故障、网络、证书那边查。这次的关键就是「登录成功但渲染失败」这个组合缩小了范围。

## 一句话版本

自托管服务的客户端会自动更新到你没准备好的版本。定期跑镜像版本检查，别等客户端替你报警。判断服务端是否真的升级了，看它自己报的运行时版本，不看你改的配置文件。
