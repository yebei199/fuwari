起因很小：网页端的用量页面显示这一周用了 7%，我终端状态栏上的 `7d` 写着 19%。两个数字都来自同一个账号、同一个时刻，却差了一倍还多。

顺着查下去，牵出了三件本来不打算一起处理的事。这篇记录它们各自的结论，以及为什么第一个判断往往是错的。

## 一、19% 不是显示错误，是缓存冻住了

状态栏的额度段不是直接渲染当前实例的数据。Claude Code 每次 API 响应会把额度快照塞进状态栏负载的 `rate_limits` 字段，但那只是**这个实例最近一次响应**的快照。开着五个终端时，四个闲置实例会各自显示自己那份陈旧数据。

所以额度段脚本维护了一份共享缓存，把每次渲染收到的快照合并进去，让所有实例渲染同一份最新数据。合并规则原本是这样：

- `resets_at` 更晚的，说明窗口翻篇了，整体替换；
- `resets_at` 相同（同一窗口内），取 `used_percentage` 较大者。

第二条的依据是「同一个窗口内用量单调不减」。这个前提听起来是常识——你只会用得更多，不会用得更少。

它错了。服务端调整额度上限时（我这边当时挂着一个限时提升 50% 的活动），分母变了，同一个窗口内的百分比会**回落**。7d 从 19% 掉到 7%，而「取较大者」把 19 死死焊在缓存里，直到窗口重置才会消失。整整一天，状态栏都在报一个偏高的假数。

验证方法很直接：把缓存文件挪走，等状态栏重新播种，看新写进来的值是多少。

```bash
mv ~/.cache/ccstatusline/rate-limits-shared.json{,.bak}
# 等十秒
cat ~/.cache/ccstatusline/rate-limits-shared.json
# {"five_hour":{...,"used_percentage":54},"seven_day":{...,"used_percentage":7}}
```

7%。缓存里那个 19 是历史遗迹。

### 换成什么规则

需要一个能区分「新旧」而不是「大小」的信号。负载里没有快照时间戳，但有 `transcript_path`——会话记录文件的路径。活跃实例每收一次 API 响应就往里写，闲置实例的这个文件停在上次响应那一刻。拿它的 mtime 当快照时间的代理：

```jq
def merge(a; b):
  if a == null then b
  elif b == null then a
  elif (b.resets_at // 0) > (a.resets_at // 0) then b
  elif (b.resets_at // 0) < (a.resets_at // 0) then a
  # 同一窗口:更新鲜的快照赢
  elif (b.seen_at // 0) >= (a.seen_at // 0) then b
  else a
  end;
```

这是个代理量，不是真值：两个都在活跃的实例，在一分钟内可能短暂互换先后，下一次响应就会收敛。代码里留了 `ponytail:` 注释标明这个上限——要精确，得让 Claude Code 在负载里带上快照时间戳，那不是我能改的。

**可复用的结论**：任何「取较大者 / 取较小者」的合并规则，背后都藏着一个单调性假设。写下它的时候把这个假设也写下来，否则它失效时不会报错，只会静静地给出错误答案。

## 二、Fable 额度：数据在，但不在负载里

网页端的用量页面有三行：当前会话、本周全部模型、本周 Fable。状态栏只有前两行。

我先去二进制里确认了数据的来源边界：

```
$ strings claude | grep -o 'anthropic-ratelimit-unified-[a-z0-9-]*' | sort -u
anthropic-ratelimit-unified-5h-utilization
anthropic-ratelimit-unified-7d-utilization
...
```

Claude Code 的 `rate_limits` 是从 HTTP 响应头拼出来的，而响应头只有 5h 和 7d 两个窗口。按模型拆分的桶根本不在这条链路上——它只存在于 OAuth 接口 `/api/oauth/usage` 的返回里，网页端和 `/usage` 对话框调的都是它：

```json
{
  "kind": "weekly_scoped",
  "percent": 8,
  "resets_at": "2026-09-07T23:00:00.429492+00:00",
  "scope": { "model": { "display_name": "Fable" } }
}
```

上游的 ccstatusline 有现成的 `fable-weekly-usage` widget，它的实现正是去调这个接口。但这个仓库的自检明确禁止任何这类 widget——禁令是两个月前一次排查留下的，当时的理由是「拿凭据发请求，换回来两个恒为零的数字」（那次涉及的是已经废弃的 Opus / Sonnet 周额度桶）。

这里要分清两层理由：

1. **花钱买零**：对废弃字段成立，对 Fable 不成立，它是真实且有区分度的数。
2. **把登录凭据交给第三方**：仍然成立。ccstatusline 是 bun 装的 `@latest` 包，每次刷新都是当时的最新版本，没人审过。开那个 widget，等于让一个自动更新的第三方程序持有你的登录 token。

第二层才是真正的约束，而它约束的是**谁拿着凭据**，不是**能不能查**。所以方案是：自己查，第三方只负责显示。

### 实现上的三个约束

取数写在额度段脚本里（几十行 shell，落在 nix store 里，内容变了 hash 就变）：

- **节流**：一个戳记文件控制，所有实例合计五分钟最多一次请求。先 `touch` 再取，免得每个实例都跟着发。
- **不阻塞**：请求在脱离的后台子 shell 里跑，三个 fd 全部重定向。不这么做，ccstatusline 会等这条管道的 EOF 直到 curl 结束——状态栏每次渲染卡五秒。
- **token 过期不发**：`expiresAt` 是毫秒时间戳，过期就跳过，等 Claude Code 下次请求刷新后再取。

有个小坑值得记：接口返回的 `resets_at` 是带微秒和 `+00:00` 的 ISO 串，jq 的 `fromdateiso8601` 两样都不认，得先削成 `...Z`：

```jq
.resets_at | sub("\\.[0-9]+"; "") | sub("\\+00:00$"; "Z") | fromdateiso8601
```

自检守的性质也相应改了：从「谁都不许碰凭据」变成「ccstatusline 自己的取数路径永远不跑」，另外加两条断言——戳记过期时脚本要派出取数，戳记新鲜时必须安静。夹具预先种好缓存和戳记，整套自检不触网。

**可复用的结论**：一条禁令写下来的时候通常绑着具体场景。换了场景要重新拆解它的理由，而不是照着字面执行或者整个推翻。这条禁令里有一半今天不成立，另一半今天仍然成立，而仍然成立的那一半只约束实现方式，不约束功能本身。

## 三、被我信了太久的一个数字

Fable 加进去之后，第四行放不下了。我做了两处妥协：Fable 不给倒计时（和 7d 共用重置时刻，说得通），7d 的倒计时从 `5d19h` 砍成 `5d`（纯粹为了省三列）。

然后用户问：这一行明明很宽敞，怎么会放不下？

自检里写着 `CCSTATUSLINE_WIDTH=96`，注释是「96 是这台机器 kitty 的实际列数」。这个数不知道什么时候起就不对了。查真实值：

```bash
# 找到会话所在的 pts，再问它的窗口尺寸
$ stty -F /dev/pts/2 size
80 159
```

159 列。我一直在按真实宽度三分之二的预算挤版面，而「放不下」这个前提本身就是错的。

新预算取 119 列 —— 实测 159 减去压缩提示要占的 40 列。顺便把窄窗口的情况明确写进注释：平铺成半宽时终端约 79 列，第四行尾部会截断，这是接受的，因为该行按重要性排序，额度在最前，先被截掉的是 `session`、`skill` 这些次要项。腾出来的列还给了 7d 的倒计时精度。

**可复用的结论**：注释里写着「这是实测值」的常量，和没有注释的常量一样会过期，而且更危险——它看起来是有据可查的。要么让测试自己去量，要么把测量方法写进注释，让下一个人能一行命令复核。我选了后者，注释里现在有那条 `stty` 命令。

## 四、最后那个多余的判断

Fable 最初渲染成光秃秃的 `fable 8%`，而 5h 和 7d 都带着 pace（用量% 减去窗口已过时间%，负数表示用量落后于时间）。

我当时的理由是：Fable 是 7d 的子集，窗口相同，pace 必然与 7d 同向，是重复不是信息。

用户不接受，我照做了。做完发现他是对的：截图里 7d 是 8%、Fable 也是 8%，那是**恰好重合**，不是必然。两者可以差很多，而整行里唯一没有参照的数字，偏偏是标着模型名的那个。

改动顺带把 pace 的算法和窗口钳位从渲染函数里提了出来，两个窗口长度也从重复的字面量改成具名的。最终形态：

```
5h 23%(-32) ↺2h13m · 7d 61%(-10) fable 8%(-63) ↺1d23h · session 18m · skill none
```

**可复用的结论**：「A 是 B 的子集所以 A 的信息冗余」——这个推理在集合上成立，在数值上不成立。子集的比例和全集的比例是两个独立的数，恰好相等不代表恒等。

## 小结

四件事，四个错误前提：

| 判断 | 错在哪 |
|---|---|
| 窗口内用量单调不减 | 分母会变，百分比会回落 |
| 不能查按模型拆分的额度 | 禁令约束的是凭据归属，不是功能 |
| 终端只有 96 列 | 注释里的「实测值」早就过期 |
| 子集的 pace 是冗余 | 恰好相等不是恒等 |

共同点是：每一个都不会以报错的形式暴露，只会安静地给出一个看起来合理的结果。发现它们靠的都不是调试，而是有人（包括我自己）拿真实数据对了一次账。
