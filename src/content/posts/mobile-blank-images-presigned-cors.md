报障是一句话:**手机 App 里图片全是灰块,桌面端一切正常。**

结论先说:问题在对象存储桶从来没配过 CORS,和客户端版本毫无关系。但我先花了大半天,基于一个严丝合缝的假设,把整个手机客户端重编了一遍——那个假设解释了全部症状,却是错的。这篇写的主要是它为什么诱人,以及我本该在哪一步停下。

## 先把服务端一项项排除掉

初始信息只有「图片看不到」。先建立事实,而不是先建立理论:

- 图片确实在对象存储里,今天上午刚写进去,大小和时间都对得上;
- 下载下来看,是标准的 1080×1543 PNG,不存在什么移动端渲染不了的尺寸或格式;
- 域名对手机可达,换移动端 UA、换桌面 UA、走代理、不走代理,四种组合响应完全一致;
- 服务端的 CORS 头是对的,WebView 那两个特殊 origin 都被正确放行,而且带 credentials;
- 服务端日志里确实有一堆告警,但读下来是全文索引写入失败,和图片无关。

到这里,服务端能查的都查了,每一项都正常。

## 那个诱人的假设

上个月我刚写过一篇结论很清楚的文章:自托管服务的客户端走公共分发渠道自动更新,服务端在你自己机器上手动更新,于是**客户端只会越来越新,服务端只会越来越旧**,差距单调扩大,直到某天客户端按新契约渲染、拿不到期待的字段而崩掉。

而这次的时间线简直是照着那篇文章长的:

- 手机上装的是自己 fork 编译的包,基座是三周前的一个 canary 开发快照;
- 服务端两天前刚升过版本;
- 症状是「文字同步正常、图片单独失效」——正好是那种登录成功之后才发生的局部渲染失败。

三条对齐,假设成立得毫不费力:canary 快照带着未发现的回归,或者两端契约对不上。

于是我做了一整套逻辑上正确的工作:把 fork 自己的几个构建提交 cherry-pick 到和服务端完全同版本的稳定 tag 上,重新出包。

这套工作本身没白做,途中还解决了几个真问题:

- NixOS 上 `yarn install` 会挂在某个包的 postinstall 上,它要下载的数据库引擎没有 NixOS 构建,404 直接让整个安装失败。手机包根本不需要那个包,`--mode=skip-build` 跳过即可;
- 构建产物默认只带 v1 JAR 签名,targetSdk 36 的 Android 拒装,得用 `apksigner` 重新签出 v2/v3;
- 原来的签名密钥密码丢了,只能新生成一把。而这一步顺带暴露了一个真正的安全缺口:fork 是公开仓库,`.gitignore` 里挡的是一个**确切的文件名**,新生成的密钥文件名不一样,根本不在规则里。改成通配后才安全。

新包装上手机,打开文档——**一模一样,全是灰块。**

## 转折是一行错误文本

这次截图里,灰块下面多了一行字:

```
blob download error: NETWORK_ERROR: Network error: Failed to fetch
```

`Failed to fetch` 是浏览器在**请求根本没能发出去或响应被拒绝**时给的错,不是服务端返回了错误码。这和我前面测出来的「服务端一切正常」并不矛盾——因为发请求的根本不是我 curl 的那个地址。

顺着这行文本去读源码,答案在三十行之内:

```ts
const SHOULD_MANUAL_REDIRECT =
  BUILD_CONFIG.isAndroid || BUILD_CONFIG.isIOS || BUILD_CONFIG.isElectron;
```

取图片时,如果命中这个常量,请求会带上 `?redirect=manual`;服务端此时不返回图片字节,而是返回一个**预签名 URL**;客户端再拿这个 URL 去直连对象存储。

这就把一切解释清楚了:

- 手机 App 命中这个常量,所以它最终是拿 WebView 去 fetch 对象存储的域名——**一个跨域请求**;
- 桌面浏览器不在这个集合里,服务端直接把字节代理回来,同源,所以从来没暴露过问题;
- 而那个对象存储桶,从建起来就没配过 CORS。

验证只要两条命令:对桶发一个 OPTIONS 预检,403;发普通 GET,响应里没有任何 `Access-Control-*` 头。浏览器于是拒绝把响应交给页面,报 `Failed to fetch`。

修复是给桶加一条 CORS 规则。这一步还被权限挡了两次:配置文件里那对对象存储密钥是**对象级**读写权限,改桶设置需要管理级;而基础设施里那个云平台令牌压根没有对象存储权限。最后是在控制台点了一下——顺带也解释了为什么这桶从来没配过 CORS:平时用的密钥根本没这个权限,不会有人「顺手」配上。

配完之后,手机端不用重装、不用改任何东西,重开文档图片就出来了。

## 为什么 origin 放开 `*` 是合理的

配之前我犹豫过一下,想清楚了就不犹豫了:

**CORS 不是访问控制。** 它只是让桶在响应里多几个头,告诉浏览器内核「允许跨域页面的 JS 读这个响应」。真正的门禁是签名验证:没有有效的预签名 URL,请求照样被拒,配不配 CORS 都一样。放开 origin 放开的是「浏览器愿不愿意把响应交给页面」,不是「谁能访问桶」。

**而且收紧到具体 origin 在这里没有意义。** 手机 WebView 的 origin 是 `https://localhost` 或 `capacitor://localhost`,桌面客户端发出的可能是 `null`——而按 CORS 规范,放行 `null` 和放行 `*` 在安全上等价,任何沙箱页面都能声称自己是 `null`。枚举清单最终等效于 `*`,只多了一份要跟着客户端形态维护的配置。签名才是门,门上再刻名单没用。

## 我本该在哪一步停下

**一、上一次的教训会变成这一次的偏见。**

这是我最想记下来的一条。上个月那篇文章的结论没有错,它今天依然成立。错的是我把它当成了模式匹配的模板:症状对得上、时间线对得上,就直接采信。

但一个假设的可信度,取决于**它排除了什么**,不取决于它解释了什么。「版本差」解释了全部症状,却没有排除任何一种其他可能——它和「桶没配 CORS」对观测到的现象给出完全一样的预测。两个假设预测相同时,先做的应该是找一个能区分它们的观测,而不是挑那个自己更熟的去动手。

区分它们的观测其实一直都在:如果是版本契约对不上,通常表现为某些图片坏、某些正常,或者某种尺寸/格式坏;而通道级的故障是**全坏**。我在拿到「全坏」这个信息之前就已经开始重编包了。

**二、客户端的错误文本是一等证据。**

我在服务端翻日志、测 UA、测代理、读容器日志,花了大量力气去构造证据,而真正的答案一直显示在用户的屏幕上,只差一句「截个图给我看看」。自托管排查有个天然的倾向:因为服务端是你能登上去的那一头,你会不自觉地只在那一头找。但故障发生在客户端,客户端才是第一现场。

**三、自托管有一类「只有部分客户端才会踩」的配置缺口。**

托管版里,对象存储直连这条链路是供应商替你配好的,你根本不会知道它存在。自托管时它变成了你的责任,而它的隐蔽之处在于:**它只在某些客户端形态上才被走到。** 浏览器用得好好的,直到某天你装了原生 App。这类缺口会长期潜伏,而且触发时机由你用哪个客户端决定,不由你的部署决定。

**四、白干的活要诚实标记。**

那个重编的新包并没有修好这个 bug。它顺带解决了几个真问题(NixOS 构建、签名方案、公开仓库的密钥泄漏风险),但把它记成「修复图片问题的版本」就是在给未来的自己留假证据——下次再出问题,我会以为这条路已经验证过了。

## 什么情况下这套判断不适用

- **图片是部分坏而不是全坏**:那更可能是数据本身的问题(某些格式、某些尺寸、某次上传中断),回到版本契约或存储完整性那边查。
- **客户端和服务端都由你分发**:不存在版本倒置,也通常不会有这种「某些客户端形态才走的隐藏链路」。
- **纯浏览器访问**:这个坑根本不会出现,因为服务端会代理字节。也正因如此,只用浏览器验证过的自托管部署,不能算验证过原生客户端。
