要在两个方案里选一个：每加一个服务写一行配置，还是让反向代理直接监听一整段端口、新服务零配置
就有 HTTPS 入口。后者显然更省事，唯一的疑虑是内存 —— 几千个监听端口值多少钱。

于是我去量。量错了，而且错了不止一次。

## 第一次：量了个不存在的配置

测试脚本起一个 caddy，监听 `:13000-14999`，测 RSS：

```
监听端口数   RSS      线程
1            46 MB    15
3001         64 MB    29
4000         70 MB    23
```

结论顺理成章：4000 个端口只比 1 个多 24MB，每端口约 6KB，线程数根本不随端口涨。缩小范围只能省
6MB，不值当。于是「那就全开吧」。

上线之后：

```
VmRSS:  707332 kB   ← 690MB
```

**差了十倍。**

原因很蠢但很典型：测试配置是这样的

```
:13001 {
	respond "ok"
}
```

而要上线的配置每个监听都要终结 TLS：

```json
"tls_connection_policies": [{}],
"automatic_https": { "disable": true }
```

我量的是「4000 个 socket 值多少钱」，要上线的是「4000 个 TLS 监听值多少钱」。这两件事差
25 倍：带 TLS 是约 159KB/端口，纯 HTTP 是约 6KB/端口。

测试脚本是我为了测**端口段这个特性能不能用**写的，能用之后我直接拿它去测性能了，没意识到
中间少了一个开关。

## 第二次：外推

重新量，这次配置形状和上线的一致：

```
监听端口数   RSS       线程
1            47 MB     14
3001         524 MB    33
4000         679 MB    33
```

679MB 和线上的 690MB 对得上，模型看起来立住了：约 159KB/端口，两个数据点算出来一致。

于是收窄到 500 个端口，按 `47 + 500 × 0.159 ≈ 126MB` 报给对方。实测：

```
TLS 500 ports   ports=500   RSS@6s=77MB   RSS@30s=77MB   threads=32
```

**77MB，不是 126MB。** 500 个端口时每端口约 60KB，3001 和 4000 时是 159KB —— 不是线性的。
两个高位数据点碰巧一致，让我以为找到了规律，其实只是在那个区间附近恰好平坦。

## 第三次：reload 不是 restart

收窄配置上线后再看，RSS 是 **764MB** —— 比 4000 个端口的时候还高。

```
$ systemctl show caddy.service -p MainPID -p ExecMainStartTimestamp -p NRestarts
MainPID=2735051
NRestarts=0
ExecMainStartTimestamp=Sun 2026-08-16 20:05:13 +08

$ journalctl -u caddy.service | tail
20:20:46 Reloading Caddy...
20:20:46 Reloaded Caddy.

$ grep -E "VmHWM|VmRSS" /proc/2735051/status
VmHWM:	  782580 kB
VmRSS:	  782580 kB
```

进程是 20:05 用**旧配置**起的，20:20 只是 reload。NixOS 的 caddy 模块默认
`enableReload = true`，配置变化走 `reloadTriggers` 热加载，不重启进程。所以这个进程还背着
4000 监听时期的堆，Go 又不会及时把释放的内存还给 OS。

识别信号是 `VmHWM == VmRSS`：当前占用等于历史峰值，说明从峰值以后一点都没回收。

放着不管，二十分钟后自己掉到了 179MB，之后就不动了 —— 干净启动是 77MB，差的 100MB 是碎片，
不重启拿不回来。

## 第四次：成本不只有内存

`final-check` 跑出一个测试失败：

```
tests/zhihu_open_api.sh
OSError: [Errno 98] Address already in use
```

那个测试的桩服务器写死绑 `18923`，而当时部署的 caddy 覆盖 `18000-19999`，把这个端口占了。

这是我从头到尾没量过的一类成本：**caddy 绑掉的端口，整台机器上别人就不能绑了。**
内存表里没有这一列，是仓库自己的测试撞出来的。收窄后的段止于 18199，测试恢复通过。

## 规则

1. **基准配置必须和上线配置同形状。** 差一个开关就可能差一个数量级。写测试脚本的目的如果中途
   变了（从「验证特性可用」变成「测量成本」），停下来重新检查配置，而不是接着用。

2. **不要外推，在目标点上测。** 两个数据点连成的直线看起来很有说服力，尤其当它们互相印证的时候。
   要用哪个规模就测哪个规模。

3. **改完配置先确认是 reload 还是 restart。** `ExecMainStartTimestamp` 和 `NRestarts` 一看便知。
   `VmHWM == VmRSS` 说明当前值就是历史峰值，那个数字属于上一版配置，不属于现在这版。

4. **资源不只有内存。** 独占端口、fd、inotify watch、systemd unit 数量都是资源，而且这类资源的
   冲突表现为「别的东西起不来」，不会出现在你正在看的那张表里。

5. **报数字的时候说清楚测的是什么形状。** 这是最要紧的一条。前三次错误里，只有第一次造成了实际
   后果 —— 因为我把「差 6MB」这个结论交给对方去做决定，对方基于它选了全开。如果当时说的是
   「4000 个纯 HTTP 监听差 6MB，带 TLS 没测」，这个决定根本不会以那种方式做出。

   数字本身错了可以改，但一个被当作决策依据的错数字，会连带作废后面所有基于它的选择。

## 边界

这些数字是 Caddy 2.11 在 Linux 上的观测值，换版本、换实现（nginx 的 `listen` 段、HAProxy 的
`bind` 段）都可能完全不同 —— 不要拿这里的 159KB/端口去估别的东西。能带走的是方法：**同形状、
不外推、区分 reload 和 restart、把非内存成本也列进来**。
