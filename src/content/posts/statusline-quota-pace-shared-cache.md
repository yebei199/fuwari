## 一个数字不构成判断

我的 Claude Code 状态栏第四行一直显示两个额度百分比:5 小时窗口用了多少,7 天窗口用了多少。
比如 `5h 27%`。

这个数字看起来有用,实际上没法据它做任何决定。27% 是多还是少,取决于这个窗口已经过去了多久。
如果才过去 10 分钟,27% 意味着我正在以六倍速烧额度,再这么下去会在重置前撞墙;如果已经过去
四个半小时,27% 说明我这个窗口基本白买了。同一个数字,两个相反的结论,而做出结论所需的另一半
信息——时间过了多少——就在旁边的倒计时里,却要我每次心算。

所以真正该显示的不是用量,而是**用量进度与时间进度的差**。我把它叫 pace:

```
pace = 用量百分比 − 窗口已过时间百分比
```

正数是超前(烧得比时间快,有撞墙风险),负数是落后(有富余),零附近是匀速。现在那一行长这样:

```
5h 51%(+5) ↺2h43m · 7d 42%(+8) ↺4d15h
```

`(+5)` 的意思是:五小时窗口已经过去约 46%,而额度用了 51%,快了 5 个百分点。这是一个可以直接
据以决策的数字,不需要再看别处。

倒计时前面那个 `↺` 原本是 `reset` 字样。加上 pace 之后一行放不下——我的终端 96 列,状态栏
自检里有一条硬性约束是每行不超过 90 列。省掉一个单词换来一个能做判断的数字,这笔交易划算。

## 多实例数字不一致,原因不是探测太少

我同时开三四个 Claude Code 实例,它们显示的剩余额度经常互相矛盾。第一反应是「探测频率不够,
或者各自探测导致不一致」,于是想去调探测间隔。这个方向是错的,而且错在对数据来源的误解。

状态栏的额度数字压根不是探测来的。Claude Code 每次向 API 发请求,响应里会附带一份
`rate_limits` 快照,状态栏渲染时照抄。所以:

- 不存在重复请求的浪费——一次额外的网络请求都没有;
- 不一致的真正原因是**每个实例只握有自己上一次请求时的快照**。闲了两小时的实例,数字就停在
  两小时前。

看清这一点之后,解法就从「调频率」变成了「让所有实例共享同一份最新快照」,而且这个解法不需要
增加任何请求。

## 共享缓存:让单调性替代时间戳

做法是一个文件 `~/.cache/ccstatusline/rate-limits-shared.json`,里面只存两个桶:

```json
{"five_hour":{"used_percentage":54,"resets_at":1787223000},
 "seven_day":{"used_percentage":42,"resets_at":1787612400}}
```

每个实例每次重画状态栏时:读缓存 → 把本次从 stdin 拿到的快照合并进去 → 用合并结果渲染,并把
新结果写回。合并规则只有两条:

1. `resets_at` 更晚 → 窗口已翻篇,整体替换;
2. `resets_at` 相同 → 取 `used_percentage` 较大者。

第二条是整个方案的支点。同一个窗口内用量只增不减,所以**「较大者」等价于「较新者」**。这意味着
我不需要给每份快照打时间戳,也不需要比较谁更新:闲置实例送来的陈旧低值天然压不倒新值。一个
本该需要版本号或时间戳的合并问题,被数据自身的单调性消掉了。

值得强调的是这条性质是有前提的,而前提我只做了部分验证。它成立依赖「5 小时额度是固定边界窗口」
——`resets_at` 的存在支持这个判断,而且我拿旧的一份 API 响应交叉核对过:两个来源给出的重置时刻
是同一个边界(一个精确到秒,一个带小数),周额度百分比也完全一致。但如果它实际是滑动窗口、用量
会下降,取最大值就会让数字偏高直到重置。我把这一点作为推断写进了注释,而不是当成事实。

## 那个被测试放过去的 bug

脚本一次输出两行:第一行是合并后的缓存 JSON,第二行是渲染文本。shell 端原本这样拆:

```sh
merged=${out%%$'\n'*}
seg=${out#*$'\n'}
```

看着没问题,跑了几十次也没问题。但两个桶都没数据时,第二行是**空字符串**——命令替换会把它
连同换行一起吃掉,于是 `out` 里根本没有换行,`${out#*$'\n'}` 匹配不到分隔符,按 POSIX 语义
**原样返回整个字符串**。结果是状态栏上直接打出:

```
{"five_hour":null,"seven_day":null}
```

这个 bug 的性质值得琢磨。它不是逻辑写错,是**参数展开在「没有匹配」时的兜底行为恰好是最坏的
那个**:不报错、不返回空、而是把输入原样吐出来。同一段代码在有数据时永远正确,只在缓存为空
且负载里没有额度字段时炸——也就是刚清掉缓存后的第一次渲染。

修法是不再依赖参数展开,改用 `read` 逐行取:

```sh
{ IFS= read -r merged; IFS= read -r seg; } <<< "$out"
```

`read` 在读到 EOF 时会把变量赋成空串而不是留作未定义,所以在 `set -u` 下也安全——这一点我先
写了三行 bash 实测确认,而不是照记忆下笔。

## 沉默不等于通过

更值得记的是:我**当时已经写了针对无数据场景的测试**,而它通过了。

那条测试喂一份最小负载(没有额度字段),断言进程退出码为 0 且 stderr 没有异常。两条断言都成立
——脚本确实没崩,它只是安静地把 JSON 打进了状态栏。测试看的是「有没有炸」,而 bug 的表现是
「输出了不该输出的东西」,两者正交。

雪上加霜的是另一层:那条测试跑的时候,共享缓存已经被前面的测试用例写进了数据。所以它连
「无数据」这个分支都没走到,测的是一条带数据的路径。测试之间通过一个共享的缓存文件互相污染,
而这种污染是**让测试变宽松**的方向,不会以失败的形式暴露自己。

补上的测试因此有两个要点:用独立的空缓存目录(不与其他用例共享状态),以及断言输出内容而不是
退出码——只要输出里出现 `{` 或桶名就算失败。我先确认这条测试在未修复的脚本上失败、修复后转绿,
才承认它有效。一条没见过红的测试不能算测试。

## 空闲实例永不重画:先查原生开关

共享缓存保证的是「实例一旦重画就用最新数据」,不保证「闲着也会自动更新」。所以下一个问题是
重画频率。

我先实测:写了个小脚本扫 `/proc`,90 秒内统计每个 Claude Code 实例起了多少个渲染子进程。结果是
当前活跃实例渲染了 9 次(全跟着事件走),而闲置两小时的实例**一次都没有**。默认是纯事件驱动,
这条路确认了。

这里的诱惑是自己造一个定时器——写个 systemd timer 定期刷缓存,或者在脚本里起后台循环。都不必:
Claude Code 原生就有 `statusLine.refreshInterval`,在事件驱动之外每 N 秒强制重画。

但我没有直接照文档写。文档说单位是秒,我在本机 CLI 二进制里把 schema 挖出来核对了一遍:
`refreshInterval` 带 `min(1)` 约束,描述是「每 N 秒在事件驱动之外重跑」,内部乘 1000 转成毫秒。
单位、边界、语义三样都对上,才落进配置。设成 60 秒——额度倒计时的粒度就是分钟,pace 变化缓慢,
更快的刷新不会多给出任何信息,而每次重画只是本机起一个约百毫秒的进程,零网络请求。

## 为什么不上 SQLite

「多个进程读写同一个文件」听起来就该上数据库或者加锁。这里不需要,理由是把两种并发问题分开看:

**撕裂读**——读到半个文件——是致命的,但已经不存在。写入走「同目录 `mktemp` 建临时文件 → `mv`
原子替换」,rename 在同一文件系统上是原子的,读者要么看到完整旧文件要么看到完整新文件。这正是
SQLite 用日志机制解决的那个问题,一次 rename 就解决了。

**丢失更新**——两个实例同时读-改-写,后写的覆盖先写的——存在,但是良性且自愈的。每个实例写入的
只是它自己的最新快照,而它下一次重画(现在最多 60 秒后)会把同一份快照重新合并进去;加上合并
规则单调,误差不累积。最坏后果是某个实例的显示短暂偏旧一分钟。

为一个自愈的、纯展示用途的毫秒级竞态引入 SQLite,代价是新依赖、WAL/journal 伴生文件、锁超时
处理,而合并逻辑一行都省不掉。真要做到严格无丢失,正确的升级路径也不是数据库而是 `flock`:在
读-合并-写外面套个文件锁,三行代码。我把这条路径写成注释留在脚本里,而不是现在就实现。

现在这份数据是一个 117 字节、两个键的文件。离需要数据库还差好几个数量级。

## 边界

这套做法有几个明确不适用的地方,写下来免得以后自己误用:

- **缓存是每台机器一份。** 多台机器之间不统一,要统一得把文件放共享存储上。
- **单调合并只对单调数据成立。** 换成任何会下降的指标(余额、并发数),取最大值立刻变成错误。
- **`resets_at` 必须完全相等才走「取较大值」分支。** 如果不同版本的客户端对这个时间戳取整方式
  不同(差 1 秒),就会退化成「更晚者整体替换」,此时一份陈旧快照可能把显示拉低。这是推断的
  风险,我没有观察到它发生。

最后一点感想是关于顺序的:这次真正有价值的产出不是 pace 那个公式(它是小学算术),而是「先搞清
数据从哪来」这一步。如果一开始就照着「探测太频繁」的直觉去调间隔,会在一个根本不存在的问题上
写一堆代码,而真正的原因——每个实例只握着自己的旧快照——会一直留着。
