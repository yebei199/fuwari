## 起因:一只不肯自己回来的手柄

一台红魔平板(RedMagicOS 11.5 / Android 16),配一只飞智八爪鱼 2 蓝牙手柄。
问题很具体:**手柄关机再开机,不会自动连回**。每次都得下拉设置、进蓝牙、找到那台
设备、点一下"连接"。玩之前一遍,中途掉线一遍,一天十几遍。

而同一台平板上的罗技鼠标一切正常——关了再开,自己就回来了。

**机制是有的,只是不给这只手柄用。**这句话是整个项目的起点:如果系统压根不支持
后台回连,那就是设计如此,认了;但既然鼠标行、手柄不行,那就是某处出了岔子,而
岔子是可以被找出来的。

## 第一步:先证明这不是错觉

在写任何代码之前,先抓包。开发者选项里打开蓝牙 HCI 日志,把手柄关掉再开,导出
btsnoop 分析:

- 手柄以**配对记录中完全相同的地址**连续发出 272 次可连接广播
  (`CONNECTABLE + scannable`);
- 同一时段,主机发出的 `LE Create Connection` 次数:**零**。

对面在不停地喊,这边一次都没应。这条证据把问题从"感觉不好用"变成了"主机侧不发起
连接",范围一下子收窄。

**这一步值得单独强调:在动手修之前,先把现象钉成一个可证伪的命题。**没有这 272 比
0,后面每一次失败的尝试我都会怀疑是不是自己搞错了前提。

## 第二步:一个看起来成功、实则无效的方案

第一版实现走的是最直觉的路:`connectGatt(device, autoConnect = true)`。这是
Android 的"后台连接"语义——把设备挂进系统的等待名单,它一广播链路就自动拉起。

结果很微妙:**链路确实拉起来了**,应用能收到 `onConnectionStateChange`
`connected=true`,能做服务发现,能读特征。但是——

- 系统设置里,那台设备照旧显示"未连接";
- 手柄照旧不能用,摇杆按键一个都没反应。

原因是我一开始没想明白的一件事:**应用建的 GATT 链路,和系统的 HID 输入服务是
两回事。**前者只是一条 ATT 通道,后者要求系统的 HID host profile 去接管这个设备、
把它注册成输入设备。ACL 链路起来了不等于 profile 接管了。

这一课的代价是好几个小时,收益是后面所有验证的标准变了:**从此不看"连上了没"
(应用视角),只看设置界面显示什么、`dumpsys input` 里有没有这台设备**。这是一个
真正跨过了系统边界的验收标准,应用自己的状态说了不算。

## 第三步:找到真正管用的那个动作

设置界面里点"连接"到底调了什么?顺着 Settings 的源码找下去,是
`BluetoothDevice.connect()`——它内部是 `connectAllEnabledProfiles`,会让系统把这台
设备上所有启用的 profile(对手柄来说就是 HID)全部接管。

这个方法是隐藏 API,而且需要两个权限:

- `BLUETOOTH_PRIVILEGED`
- `MODIFY_PHONE_STATE`

两个都是 `signature|privileged` 级别。**普通应用申请不到,用户也授不了**,不存在
"弹个框让用户同意"这种可能。

到这里方案空间就很清楚了:要么找到一条不需要这两个权限的等价路径,要么想办法弄到
一个拥有它们的身份。

## 第四步:六条路,逐一在真机上证伪

我不想一上来就上特权方案,先把所有"正常"路径试穿。每一条都在真机上跑过:

| 尝试 | 结果 |
|---|---|
| 反射直接调 `BluetoothDevice.connect()` | 方法能拿到,系统服务端拒绝:缺 `MODIFY_PHONE_STATE` |
| 通过 `HID_HOST` profile 代理调 `connect(device)` | 被隐藏 API 名单拦下,`NoSuchMethodException` |
| 配对记录残缺(缺 HID 服务 UUID、类型不对) | 手柄的记录正常,和能回连的鼠标一致 |
| 手柄广播地址与配对记录不符 | 地址分毫不差 |
| HID 连接策略被设成"禁止" | 策略就是"允许" |
| `fetchUuidsWithSdp()` 触发系统 PhonePolicy 自己发起 | 广播确实送达,但那条分支只在策略为"未知"时才执行,而这里是"允许" |

最后一条最可惜:系统里确实有一段"发现服务后自动连接"的逻辑,只是它的触发条件恰好
和我们的状态互斥。

**把证伪清单写进 README,是这个项目做对的事情之一。**它的价值不在当时,在几个月后
——那时的我(或者别人)看到这个问题,第一反应一定是"是不是配对记录坏了""是不是
策略被关了",而这张表能直接省掉一整天。

## 第五步:借一个有权限的身份

shell 用户(uid 2000)恰好握有这两个权限。而
[Shizuku](https://shizuku.rikka.app/) 的作用正是:通过无线调试或一次 adb 启动,
把一个进程拉起在 shell 身份下,应用通过 AIDL 把请求送过去执行。

不需要 root,不改系统,不碰配对记录。

但在搭那一整套 Shizuku 用户服务之前,我先写了个探针。

## 插曲:在裸进程里唤醒蓝牙栈

**为什么要先做探针**:搭 Shizuku 用户服务是一堆活——AIDL、绑定、权限回调、生命周期。
如果 shell 身份下这个调用压根不成立,那些活全白干。所以先用 `app_process` 起一个
裸的 Java 进程(它天然就是 shell 身份),只验证一件事:这个身份能不能让系统接管
设备。

这个探针踩了两个坑,都挺有意思。

**坑一:进程一碰蓝牙就被 SIGKILL。**没有堆栈,没有异常,进程直接消失。做了个对照
探针——同样的进程,什么都不做,空转 12 秒,活得好好的。说明是蓝牙相关的操作触发的。

原因是:蓝牙适配器建好之后会往主消息循环投递回调。我只调了 `Looper.prepareMainLooper()`
准备了循环,却没有真正 `Looper.loop()` 跑起来。系统判定这个进程无响应,直接杀掉。
把所有蓝牙操作放进一个**正在运行的**循环里,问题消失。

**坑二:`manager.getAdapter()` 返回 null。**因为壳子进程没走过应用初始化流程,框架
内部的蓝牙服务注册表是空的。常规入口拿不到东西。解法是自己把注册表填上,再直接从
服务管理器取绑定器、反射构造适配器:

```java
// 应用进程由系统在初始化时填好这张注册表,壳子进程没走那一步,得自己填
Class<?> smClass = Class.forName("android.os.BluetoothServiceManager");
Constructor<?> ctor = smClass.getDeclaredConstructor();
ctor.setAccessible(true);
Class.forName("android.bluetooth.BluetoothFrameworkInitializer")
     .getMethod("setBluetoothServiceManager", smClass)
     .invoke(null, ctor.newInstance());

// 直接取绑定器,自行组装适配器
IBinder binder = (IBinder) Class.forName("android.os.ServiceManager")
        .getMethod("getService", String.class)
        .invoke(null, "bluetooth_manager");
Object manager = Class.forName("android.bluetooth.IBluetoothManager$Stub")
        .getMethod("asInterface", IBinder.class).invoke(null, binder);

AttributionSource source = new AttributionSource.Builder(Process.myUid())
        .setPackageName("com.android.shell").build();
// 再反射找那个 (IBluetoothManager, AttributionSource) 的构造函数
```

顺带一提,`BluetoothFrameworkInitializer` 的包名是 `android.bluetooth`,不是
`android.os`——我在这里浪费了一轮 `ClassNotFoundException`。

探针跑通,`disconnect()` 返回 0,系统状态真的变了。**这时候再去搭 Shizuku 那一整套
才是有把握的。**

## 架构:纯决策核心 + 能力外壳

跑通之后重构成了现在的样子:

- **`src/engine.rs`——纯决策核心。**不碰任何 Android API。输入是"发生了什么"(扫到
  广播、连接状态变了、用户点了某一行),输出是"该做什么"(连这台、启停扫描)。
  **时间是作为参数传进来的,从不自己读时钟**,所以每个用例都完全可重复。
- **`Rearm.java`——能力外壳。**只做事,不做判断。扫描、连接、读特征、查配对列表、
  发通知。
- **`Privileged.java` / `PrivilegedConnect.java`**——Shizuku 客户端与运行在 shell
  身份下的那一侧。
- **界面是 Slint**,入口是 `NativeActivity` 加载的 cdylib。

**蓝牙那半边为什么必须是 Java**:BLE 的回调类(`ScanCallback`、
`BluetoothGattCallback`)是**抽象类**而不是接口,JNI 没法从 Rust 实现抽象类。这是
硬约束,不是偏好。

这个分层的收益很实在:决策逻辑有五十多个单元测试,在电脑上秒级跑完,不需要真机。
但它也有代价,后面会说到。

## 跑通只是开始

特权连接在 2026 年 8 月 22 日跑通,设置界面显示"已连接",手柄能用。然后真正的
麻烦才开始——**一个能工作的原型和一个能长期使用的工具,中间隔着一堆运营问题。**

### 卡手:我们自己在抢射频

用户反馈"极短的高频操作会卡手,等多久也不恢复"。查下来是我们自己的锅:布防的实现
是持续扫描,而**设备已经连上之后扫描没有停**。BLE 扫描和已建立的连接共用同一个
射频,扫描窗口会挤掉手柄的输入包。系统的统计显示应用累计扫了 9,520,886 毫秒
(2 小时 39 分)。

改法是"连上即停扫,断开才复扫"。顺带查到 ROM 自己的一个组件在 19 小时 25 分的开机
时间里扫了 5 小时 42 分——那是个外部干扰源,和应用无关,但解释了为什么这台机器的
BLE 体验本来就不太好。

### 五秒回连:省电扫描每 5120 毫秒只听 512 毫秒

停扫之后又出现新问题:重连要五秒以上。原因是 `SCAN_MODE_LOW_POWER` 的占空比只有
10%——手柄广播得再勤,平均也要两秒多才被撞上,最坏五秒往上。

改成两档:刚掉线那阵子用 `SCAN_MODE_LOW_LATENCY`(满占空比)把这段等待压掉;超过
两分钟还没回来,说明手柄多半已经关机,退回省电模式,免得白烧电。实测重连降到
417 毫秒和 830 毫秒。

**这是那种"参数改一个字,效果差一个数量级"的地方**,而它不写在任何显眼的文档里,
得知道 Android 扫描模式对应的实际 interval/window 才反应得过来。

### 快信号与慢信号:一个我自己造出来的回归

平台给的连接状态有两个来源,快慢不同:ACL 广播链路一起来就到;而输入设备列表要等
HID profile 完全起来才转真,中间有几秒空窗。

我加了一条"用平台状态校正本地残留"的逻辑(防止漏掉断开广播导致扫描永不恢复),
结果让慢信号覆盖了快信号——**扫描会在链路建立中途被重开,而那正是射频最紧张的
时刻。**

修法是给链路加一个 30 秒的稳定窗口,窗口内以 ACL 事实为准,窗口外仍由平台判断兜底
(免得回到"扫描永不恢复")。

这个回归是被一轮对抗性代码审查找出来的,我自己没看出来。**引入一个防御机制时,要
问它会不会破坏另一个已有的不变量**——尤其当两个机制读的是同一份状态的不同视图时。

### logcat 是坏的

排查过程中一度以为平板的 logcat 坏了——什么都打不出来。真相是 ROM 把
`log.tag` 全局设成了 `S`(SILENT)。`adb shell setprop log.tag D` 可以恢复,但重启
后失效。

这类"环境本身在骗你"的坑,浪费的时间不比 bug 少。后来我在应用里加了一条:所有
应用内日志同时抄一份进 logcat——这样排查时不必把界面切到前台去看(用户在打游戏,
切前台是很不礼貌的)。

### 划掉最近任务 = 强制停止

有一次用户报告"手柄又连不上了",查日志发现是他在几分钟前从最近任务里划掉了应用,
而这个 ROM 的处理是 `GamePi handleTaskRemove` → 整个包被强制停止。前台服务救不了
这个——**用户主动划掉的进程,系统认为就该死。**

对应的设计决定是:前台服务返回 `START_NOT_STICKY`。因为布防的引擎和 Context 都随
界面创建而初始化,进程被回收后单独被拉回来的服务里什么都没有,它会挂着"运行中"的
通知却不扫描、不重试。**那比不工作更糟,因为它在骗人。宁可安静地不在。**

## 需要人管的时候,得说话

用户提的需求是:"如果需要人工操作就弹窗弹消息通知告诉我"。

判断放在引擎里(什么算"需要人管"是策略),Android 那侧只递两个它才知道的事实——
蓝牙开没开、特权身份就绪没有——再把返回的话显示出去。三种情况:

- 蓝牙关着;
- Shizuku 没就绪;
- 设备断开已久、重试无果(多半是手柄关机了,而按下电源键这件事主机永远做不到)。

第一版装上去之后,我查 `dumpsys notification` 发现通知通道的创建时刻正好落在应用
启动那一瞬——通道只在要弹非空通知时才创建,所以**它真的弹过一次**。原因是 Shizuku
的绑定是异步的,应用刚起来那一刻它必然"未就绪",于是弹一条、绑定完成后自己撤掉。

**通知栏一闪而过的假警报,比不提醒更让人不信任它。**改成三条分支统一先等到"有设备
久等不回"才开口,阈值取 6 分钟(略大于盲试退避的 5 分钟上限,让自动那条路先走完
再喊人)。

## 一个做不成的功能:读电量

用户想要低电量提醒。查下来三条路:

1. `InputDevice.getBatteryState()`(公开 API)——走不通。`dumpsys input` 里手柄条目
   下没有 `Batteries:` 块(那台有电量的是罗技鼠标)。
2. 蓝牙栈自己的电量上报——没有。栈里 `BATTERY` profile 是启用的,但这台设备没有
   任何电量字段。
3. BLE 标准电池服务 `0x180F`——**手柄没有这个服务**。它的 GATT 上只有
   `1800`/`1801`/`180a`/`6e400001-...`(Nordic UART 私有通道)/`1812`。

而厂商自己的 App 能显示电池图标。所以电量走的是那条私有 UART 通道。

这里有个有意思的发现:**多个 GATT 客户端共用同一条 ATT 链路**,所以厂商 App 问电量
时的回包,我们订阅了也能收到。实测确认收得到,通道上两类包靠倒数第二个字节区分:
`0xfe` 是每秒几十条的输入上报(能看出摇杆中位和陀螺仪增量),其余是状态包。

状态包二十字节,长这样(候选电量字节在里面,但不知道是哪个):

```
ac c0 5a 47 a8 2f ff ff 70 00 0x 00 00 13 00 00 60 52 fd 10
```

要定位那个字节只能做对照实验(改变电池状态看哪个字节跟着动),因为**厂商 APK 加了
壳**——反编译出来只有 `com/stub` 和几百 K 骨架,真正的 dex 是运行时由 native 解密的,
静态分析拿不到解析代码。

用户在这里叫停了:"算了我不要这功能了"。**这是对的决定**——为一个"nice to have"去
逆向一个加壳应用的私有协议,投入产出比很差。我把探针代码撤掉了,把发现写进文档。

**做不成也是一种结果,前提是你把它做到"知道为什么做不成"的程度。**

## 一个从未运行过的功能

查电量的路上,顺手挖出一个存在很久的 bug。

保活功能——每分钟给手柄发一次 GATT 读,试探能不能推迟它自动休眠——**从上线起一次都
没有真正执行过**。

```java
public static void connect(String mac) {
    // ...
    String privileged = Privileged.connect(mac);
    if (privileged != null) {
        log(privileged);
        return;              // ← 就是这一行
    }
    // 退路:自建 GATT 客户端
    gatts.put(mac, d.connectGatt(ctx, true, CALLBACK, TRANSPORT_LE));
}
```

特权连接是主路径,平时百分之百走它,一走就在那行 `return` 退出,后面建 GATT 客户端
的代码永远到不了。于是 `gatts` 永远是空的,而 `keepAlive` 的第一行是
`if (g == null) return;`。

一分钟一次,几个小时,零次发送,零条日志——因为成功不打日志,而它从来没走到"可能
失败"的地方。

**它是靠查电量发现的**:我需要一个 GATT 客户端来订阅那条私有通道,去找的时候发现
根本没有。不是靠测试,不是靠用户反馈。

三点教训:

**失败模式是"安静"的功能,可能永远不工作而没人发现。**保活的预期效果本来就模糊
("手柄少休眠一点"),没人能凭体感判断;代码路径上它连一条错误日志都不会产生。
这两件事凑在一起,就是一个可以无限期潜伏的 bug。补救很便宜:让"没做成"发出声音。

**早返回是这类 bug 的高发区。**一个入口两条路径,后加的副作用挂在其中一条上,另一条
静悄悄地绕过去。写 `return` 的时候要多问一句:这个入口后面还有别人加进来的东西吗?

**五十多个单元测试为什么全绿。**保活的决策部分测得相当细——只对布防中且已连上的
设备发、每分钟最多一次、没布防的不碰。这些用例是对的,但它们测的是"该不该发",不是
"发出去了没有"。**bug 在外壳里,而外壳没有测试。**

这不是说分层错了,纯逻辑核心的可测性是真实收益。但要清醒地认识到它的代价:**这种
分层会把 bug 系统性地挤到那层没有测试的外壳里。**外壳越薄越好,不是为了优雅,是
因为它是测不到的地方。实践上的补丁:凡是外壳里"什么都没做就返回"的分支,都留一行
日志。

## 最后一战:一次承认失败的延迟优化

剩下的问题是回连要 3 秒以上,用户希望更快。这一段我花了一下午,最后的结论是**做不到**。

### 第一次测量就是错的

手上只有两条日志:掉线的时刻,和"已请求系统连接"的时刻。于是算出:

```
14:56:38.222  链路断开
14:56:39.099  已请求系统连接    +877ms
14:56:41.317  ACL 建立         +2218ms
```

结论:扫描只花了 877 毫秒,系统建链花了 2218 毫秒,瓶颈在后半段。

**这个归因是错的**,而且错得很有欺骗性——数字都是真的,分段是假的。那 877 毫秒里
其实塞了三件事:系统广播分发、扫描启动、等待第一条广播。我没有区分它们的锚点,就
默认它们可以合并成"扫描"。

补锚点很便宜,就是在开扫和停扫各打一行日志:

```
15:46:25.326  链路断开
15:46:25.355  开扫             +29ms
15:46:27.443  停扫(扫到广播)  +2088ms
15:46:27.561  发出连接          +118ms
15:46:28.426  ACL 建立          +865ms
```

真正的大头是"开扫到收到第一条广播",两秒。跟我原先的判断正好相反。

**分段测量的可信度取决于锚点密度,不取决于数字精度。**没有锚点的地方,你以为在测量,
其实在推断,而推断会挑一个符合你预期的解释。

### 两处真实的优化

**其一,断开到开扫的 518 毫秒。**应用原来靠 `ACTION_ACL_DISCONNECTED` 广播才知道
掉线,而系统广播分发要半秒。但应用自己挂着的 GATT 客户端,它的
`onConnectionStateChange` 在链路断开后 **2 毫秒**就回调了——那条回调原本只用来关闭
客户端,没告诉决策层。接上之后:518 ms → 30 ms。

只认非零状态很重要:`status == 0` 是我们自己主动关的客户端,链路未必有事;
`status == 8`(监督超时)才是链路真的没了。

**其二,发出连接之后还在满占空比扫描。**两个独立理由,第二个不依赖任何射频假设:

1. `SCAN_MODE_LOW_LATENCY` 是 100% 占空比,接收机一直被占着,而系统的连接发起器
   要用同一个射频去等对方广播;
2. 更硬的一条:发出连接之后的重试窗口内,决策层会把收到的广播一律按"连接中"跳过
   (建链本身要几秒,不能被打断)。**既然这段时间的广播根本不会被采纳,扫描就是
   纯粹白扫。**

判据直接复用已有的重试窗口,不新增状态。顺序上要把"更新扫描"挪到"发出连接"之前,
否则停扫比连接还晚,等于没改。这一段从 2218 毫秒变成 136 / 158 / 865 毫秒。

**主机侧合计:约 2.7 秒 → 约 0.15 秒。**

### 然后我发现总时长根本没动

六次完整测量的总时长:

```
3095 ms   (优化前)
3282 ms
3137 ms
3361 ms
3100 ms
3321 ms
```

**看不出任何下降趋势。**我每砍掉一段,"等手柄开始广播"那一段就涨回来填上——1466、
2088、2525、3031 毫秒,波动幅度比我省下的全部时间还大。

我是在第五次测量时才把六个总数排在一起看的。在那之前,我一次次拿分段的胜利去汇报
进展。**每一句都是真的,合起来给人的印象是假的。**

两条教训:

**优化的验收指标是用户感知的那个数,不是你改动的那一段。**分段变快是过程证据,
总时长不变是结果。当两者冲突,结果说了算,而且要主动去看——它不会自己跳出来。

**一个跨越所有改动都保持恒定的总量,本身就是最强的信号。**它比任何单段数字都更能
说明问题:这更像一个固定计时器,而不是可以优化的开销。

### 为什么快不了:三条硬证据

"手柄不发广播"这个说法要经得起质疑,否则就是甩锅。

**扫描确实在全速听。**系统日志里扫描参数是 `160 / 160` 扫描单位。一个单位是 0.625
毫秒,所以间隔和窗口都是 100 毫秒——**窗口等于间隔,就是接收机全程在听**。同一行还有
`scanModeApp 2 scanModeUsed 2`,说明系统没有因为应用在后台把模式降级(Android 对
后台应用的扫描降级是真实存在的,必须排掉)。

**信号极强。**扫描结果里手柄的 RSSI 在 −33 到 −39 dBm。不是距离问题。

**总时长恒定。**见上。

在 −35 dBm 信号、11.25 毫秒连接间隔、3 秒监督超时下,链路判死需要**连续错过约 266
个连接事件**。这种信号强度下靠干扰凑不出这个数。更合理的解释是对面在那几秒里停止了
发送。最可能的机制是手柄自己的监督超时:日志里连接参数始终是 `timeout=300`,即
3000 毫秒。这个参数由手柄提出;应用请求高优先级时能把它拉到 5000 毫秒,但手柄会在
几秒内改回去——13 分钟内这条链路的参数被改了 47 次,其中 44 次由手柄发起,应用只
发起过 3 次。

### 顺便逐条证伪的

| 怀疑 | 证据 |
|---|---|
| WiFi 2.4G 干扰 | WiFi 工作在 5 GHz 频段,不碰 2.4G |
| 无线投屏占射频 | 外接显示器是 HDMI 有线,无 WiFi Direct 组 |
| 别的应用在扫 BLE | 同期系统统计里只有本应用 |
| 蓝牙音频抢射频 | 没有 A2DP 设备连着 |
| 射频环境整体变差 | 同一空间的蓝牙鼠标零掉线 |
| 信号弱或距离远 | RSSI −33 到 −39 dBm |

**"同一空间的鼠标零掉线"这一条特别好用**:它用一个天然的对照组,一次性排掉了所有
"环境变差"类的解释。排查时先找现成的对照组,比自己造实验便宜得多。

### 我在因果上摔的三跤

这部分比上面的数字更值得写。

**第一跤:指控保活。**某段时间掉线变密,我注意到"保活关着的 20 分钟掉 1 次、开着的
6 分钟掉 2 次",就提出把它关掉。后来把保活的读取时刻和掉线时刻并排列出来:

```
15:43:27  保活读
15:44:27  保活读
15:45:27  保活读
          15:46:25  掉线   ← 距上次读 58 秒,距下次读还差 2 秒
15:46:37  保活读
          15:47:33  掉线   ← 距上次读 56 秒,距下次读还差 4 秒
```

如果是保活在打断链路,掉线应该**紧跟在读之后**。实际两次都发生在下一次读之前几秒,
中间还有连续四次读毫无事故。**时序对不上,因果不成立。**

**第二跤:混淆变量是我自己制造的。**那段"掉线变密"的窗口里,我为了装包反复重启
应用——而当时应用有个缺陷:每次启动都会对着一台已经连着的手柄满占空比扫描整整
十秒(恢复布防时没有先问设备连没连,要等第一次巡检才纠正)。**我一边在测量掉线率,
一边在每隔几分钟往射频里扔一次十秒的干扰。**

**第三跤:用户在动硬件。**配对记录突然消失,我当成"绑定密钥自己失效"这条严重线索
分析了一通。实际原因是用户在刷手柄固件。而那之前十几分钟的密集掉线,大概率也是
手柄进入这个状态的过程中产生的——那段数据全部作废。

三跤的共同点:**在样本量支撑不了结论的时候下了结论。**具体的防御手段:

- 相关性出现时,先列出这段时间里**自己**改过什么、做过什么。自制的干扰源优先级最高。
- 时序类的指控要看**对齐**,不能只看频次。"A 多的时候 B 也多"远弱于"每个 B 都紧跟
  一个 A"。
- 硬件在场时,先问一句"你刚才动过它吗"。这个问题的成本是一句话,不问的代价是一
  下午的分析作废。

## 回头看:哪些决定是对的

**先做探针,再搭方案。**如果 shell 身份下那个调用不成立,Shizuku 那一整套就全白干。
探针的成本是一个下午,省下的可能是一周。

**把决策抽成不碰平台 API 的纯核心,时间作为参数传入。**五十多个用例在电脑上秒级跑
完,改动敢动。代价是 bug 会挤到外壳里,这一点要清醒。

**验收标准要跨过系统边界。**不看应用自己的状态,看设置界面、看 `dumpsys input`。
第一版 `autoConnect` 的教训。

**把负结果和证伪清单写进文档。**六条被证伪的路径、延迟测量的完整分段、扫描参数
`160/160` 这条记录——它们的价值不在当时,在下一次。

**该停的时候停。**电量功能停在了"知道为什么做不成";延迟优化停在了"知道剩下的时间
不归我们管"。还有一个决定是拒绝把引擎从界面拆进服务——因为 Shizuku 重启后本来就得
手动启动,反正要碰平板,拆分换不来真正的"开机即用",不值这个架构改动。

## 它适用于谁

特权连接那条路,对**任何"系统不给 BLE 设备回连"的机型**都通用,前提是装得上
Shizuku。不需要 root,不改系统,不碰配对记录。

不适用的情况也说清楚:

- Shizuku 需要每次平板重启后手动启动(无线调试或连电脑 adb),这是它的固有限制;
- 从最近任务划掉应用等于强制停止,布防会失效,这个救不了;
- 回连速度受限于外设固件,主机侧优化到头也就是 3 秒出头。
