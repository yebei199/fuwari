目标很简单:让安卓平板通过拓展坞走有线网,以尽量低的延迟玩港澳台服的激斗峡谷。结果这一天
踩穿了四层完全不同的坑,每一层的表象都指向错误的方向。最后花 35 块钱买的 VPS 被一行 adb
命令"反杀"——但这行命令本身,恰恰是折腾 VPS 的过程中才挖出来的。

## 坑一:网线插上了,系统装作没看见

拓展坞接了网线,平板却完全无感。第一反应是驱动或系统问题,实际是两件更物理的事:

1. **插错了口**。拓展坞的 Type-C 口不是等价的:有专门的 PD 供电输入口和上行数据口,
   平板必须接在上行数据口上,否则 USB 网卡根本不会枚举。
2. **供电不足导致数据损坏**。RTL8152 这类 USB 网卡在总线供电不足时,小包正常、大包损坏
   ——抓包能看到 DHCP OFFER 到达时字节已经错乱。接上 PD 电源后立刻正常。顺带,网口指示灯
   是橙色说明千兆芯片只协商到了百兆,这也是供电/线材问题的旁证。

教训:USB 网卡的故障排查,先查供电和插口拓扑,再谈软件。"能识别但数据坏"这种半死状态
比完全不识别更有迷惑性。

## 坑二:有线网上,所有 VPN 隔一分钟就暴毙

有线通了之后,更诡异的问题出现:游戏加速器(UU、帕拉斯)在有线网上完全不工作,自己装的
代理客户端(v2rayNG、NekoBox)也是启动后 55~95 秒必断,断了还连不回来。换客户端、换协议、
换服务端,现象完全一致。

这种"对所有同类应用无差别生效"的故障,大概率不在应用层。真凶是 ROM 的省电机制:这台
平板的电源管理在**以太网**上会掐掉后台 VPN 应用的 socket——WiFi 上反而没这待遇,估计是
厂商的省电策略压根没考虑过"平板插网线"这个场景。

解药是两行 adb:

```bash
adb shell dumpsys deviceidle whitelist +<包名>
adb shell cmd appops set <包名> RUN_ANY_IN_BACKGROUND allow
```

加上白名单后,NekoBox 在纯有线网上稳定存活,远超之前的死亡窗口。UU 那个"有线黑洞"
——连上加速器直接断网——追根溯源也是同一个凶手。

教训:当**多个互不相干的应用在同一场景下以相同方式死亡**时,嫌疑人是平台,不是应用。
安卓设备上任何长连接类应用出现定时暴毙,先查 deviceidle 和 appops,再怀疑网络。

## 坑三:TCP 代理打游戏,手感永远差一口气

自建节点最初用的是 VLESS + REALITY(TCP)。网页流畅,游戏却总觉得黏滞,还时不时转圈。
原因是结构性的:游戏流量是 UDP,塞进 TCP 隧道就继承了 TCP 的队头阻塞——丢一个包,后面
所有包都得等重传,这对实时游戏是灾难。中途还踩了一个配置细节:客户端的包编码必须设为
xudp,否则服务端直接报 flow mismatch,UDP 根本不通。

根治方案是给服务端加 Hysteria2 入站——QUIC 原生,UDP 直接走 UDP,丢包只影响丢的那个包。
切换后手感立竿见影。

## 坑四:一个 208 KiB 的默认值,吃掉了 18ms

Hysteria2 跑起来后延迟仍不理想,最后的收益来自一个极不起眼的地方:Debian 默认的
`net.core.rmem_max` 只有 208 KiB,而 quic-go 想要多兆字节的接收缓冲区,要不到就静默降级。
缓冲区不够,突发丢包直接变成重传等待。

```bash
sysctl -w net.core.rmem_max=7500000
sysctl -w net.core.wmem_max=7500000
```

改完之后测速延迟从 40ms 直落到 22ms。这是全天单位改动收益最高的一处——两个 sysctl,
省了 18ms。这也是个提醒:自建 QUIC 类服务,内核缓冲区调优不是"锦上添花",是必选项。

## 延迟的物理课:为什么怎么折腾都到不了 40ms 以下

进游戏后延迟仍在 20ms 和 60~70ms 之间跳,这不是配置问题,是地理问题。实测下来:

- 家里到香港的物理地板约 12ms,这是光速和路由给的,谁也压不掉;
- 港澳台服的对局服务器分布在香港、新加坡、日本**多地**,进哪个房间由匹配系统决定,
  玩家无法选择。香港房约 20ms,新加坡/日本房 60~70ms——后者的大头是香港到东南亚的
  跨海延迟,任何单点香港 VPS 都无解;
- 直连新加坡/日本对局服务器要 160ms 以上,所以代理仍然省了约 100ms,只是"省到 40ms
  以下"在物理上不存在。

教训:优化延迟之前,先把链路每一段的物理地板测出来。地板之下的目标不是难,是不存在,
早点知道能省掉大量无意义的折腾。测试也要用真实目标——用游戏对局服务器的真实 IP 测,
而不是随便找个测速网站;查 VPS 线路要用官方 Looking Glass,第三方测试站的陈旧 IP 能给
出完全相反的结论。

## 反转:35 块的 VPS,被一行白名单"反杀"

故事的讽刺在结尾。坑二挖出的白名单解药,同样救活了 UU 加速器——而 UU 是多入口多出口的
专线网络,深圳入口、新加坡/日本本地出口,结构上就比"所有流量都从香港绕"的单点 VPS 快。
白名单加上后,UU 在有线网上跑起来了,延迟比自建节点还低。

那 35 块钱买的 VPS 白买了吗?账不能这么算:

1. **没有这台 VPS,就找不到真凶**。正是自建节点提供了一个完全可控的对照组——服务端日志
   看得见、协议自己定、变量随便控——才能把"所有 VPN 都死"从玄学收敛到 ROM 省电机制。
   用黑盒的商业加速器排障,永远只能猜。
2. **它现在是备胎**,免订阅、配置完全自持,商业加速器抽风或不想续费时随时顶上。
3. Hysteria2、UDP 缓冲区、延迟测量这些经验,值回票价。

最后的格局:打游戏开 UU(专线出口延迟最低),自建节点做稳定备份,两套互为冗余。注意安卓
只有一个 VPN 槽位,两者同时只能开一个。

## 带走的清单

- USB 网卡半死不活:先查供电和拓展坞插口,橙灯 = 没协商到千兆;
- 有线网上 VPN 类应用定时暴毙:`deviceidle whitelist` + `appops`,先于一切网络排查;
- 游戏流量走代理:必须 UDP 原生(Hysteria2/QUIC),UDP-in-TCP 手感永远不对;
- 自建 QUIC 服务:`rmem_max`/`wmem_max` 拉到 7.5MB 是必选项,不是可选项;
- 优化前先测物理地板,用真实对局 IP 和官方 Looking Glass,不用路边测速站;
- 无差别杀死一类应用的故障,凶手在平台层;
- 一台便宜 VPS 作为"完全可控的对照组",排障价值可能远超它的代理价值。
