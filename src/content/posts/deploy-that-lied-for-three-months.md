起点是一句普通的报障：**AFFiNE 手机客户端说服务端版本过低，要求 ≥ 0.27。**

这看起来是上一篇写过的那个老问题——客户端自动更新跑到了服务端前面。于是我按流程做：查上游最新版、改 digest、部署、验证。部署返回 0，服务 200，`ops service verify` 通过，`/info` 有响应。

然后 `/info` 里的版本号没变。

改一次，部署，没变。再改，部署，还是没变。

## 一层层剥下去

最后挖到底，是四个问题叠在一起，从表层到根部：

**第一层：版本号写在 `.env` 里。**

compose 里是这么写的：

```yaml
args:
  AFFINE_REVISION: ${AFFINE_REVISION:-sha256:74baac63...}
```

`.env` 里有一行 `AFFINE_REVISION=sha256:74baac63...`。于是 `:-` 那个默认值**永远用不上**。我改的是 compose 和 Dockerfile 里的默认值，实际生效的一直是 `.env`。镜像 pin 工具改的也是同一批文件——它老老实实改完、报告成功，而那个值从来没有生效过。

版本 pin 是部署产物的身份，该由仓库和工具管；`.env` 是环境和密钥。混在一起的直接后果就是：**catalog 里记的版本和实际跑的镜像各说各话，而且没有任何东西会报警**，因为两边各自都自洽。

**第二层：Dockerfile 里 digest 用了 `:` 而不是 `@`。**

```dockerfile
ARG AFFINE_REVISION=sha256:...
FROM ghcr.io/toeverything/affine:${AFFINE_REVISION}
#                                ↑ digest 必须用 @
```

拼出来是 `affine:sha256:...`，一个非法引用。这个 ARG 早年存的是 tag，那时 `:` 是对的；后来改存 digest，语法就错了，没人回头改这一行。

buildkit 一直在报 `InvalidDefaultArgInFrom: results in empty or invalid base image name (line 2)`。**这条警告每次构建都出现，我把它当噪音略过了。**

**第三层：一个按字节模式匹配的补丁。**

镜像里有一层本地构建，用正则改写编译产物 `main.js`，往 nodemailer 的 SMTP 选项里注入几个字段。上游一重新编译，模式就失配，脚本抛错：

```
Error: AFFiNE mail sender patch failed: SMTP options pattern not found
#8 ERROR: process "/bin/sh -c node /tmp/patch-mail-sender.mjs" did not complete successfully
```

**第四层，也是真正的病根：部署脚本没有 `set -e`。**

远端执行的脚本长这样：

```bash
cd /root/infra
if [ -f .env ]; then set -a && . ./.env && set +a; fi
docker compose --env-file .env -f xxx.yml pull --ignore-buildable
docker compose --env-file .env -f xxx.yml build --pull      # ← 这里失败了
docker compose --env-file .env -f xxx.yml up -d             # ← 照常执行
```

`build` 失败，`up -d` 继续跑，拿本地已有的那个镜像起容器，**整个命令退出码 0**。

同一个仓库里，备份脚本是有 `set -euo pipefail` 的。部署脚本没有。

## 三个月，以及为什么没人发现

镜像的构建时间戳是 **2026-05-14**。也就是说，从那天起 AFFiNE 的每一次部署都在 build 阶段失败，又每一次都报告成功。

这三个月里，所有能看的信号都是绿的：

- `ops service deploy` 退出码 0
- `ops service verify` 通过（它检查容器在跑、环境变量匹配、HTTP 探针通）
- 服务 HTTP 200
- `/info` 正常返回 JSON

没有一条是假的。容器**确实**在跑，环境变量**确实**匹配，服务**确实**在响应——只不过是三个月前那个镜像在做这些事。

这就是静默失败最恶心的地方：**它不制造错误信号，它制造正确信号**。所有下游检查都在忠实地报告一个陈旧但健康的系统。

真正暴露它的，是一个我们控制不了的外部条件——手机客户端更新到 0.27，开始硬性检查服务端版本。如果 AFFiNE 没有这个检查，这事还会继续下去。

## 我连错了三次

比 bug 更值得记的是我自己的推理过程。我在这个问题上连续错了三次，三次是同一个毛病：**拿一个我没验证过的观测当事实，往下推结论。**

**第一次**：把 `InvalidDefaultArgInFrom` 当噪音。它每次构建都出现，出现了很久，于是它"看起来像背景音"。但一条稳定复现的警告不是噪音，是一个稳定复现的问题——它一直在准确地指认第二层那个语法错误，我没读。

**第二次，代价最大。**

我发现 `stable` tag 的 digest 和某个版本号 tag 的 digest 不同，而部署后 `/info` 报 `0.26.6`。由此我推出一套完整的理论：AFFiNE 的 `stable` 是独立的稳定分支构建线，构建时间更新但 compatibility 号更低，跟着它走会把版本升反。我还据此改了 catalog 的追踪配置，写了一大段注释解释这个"陷阱"。

**整段推理的地基，是一次失败部署的输出。** 那个 `/info` 报的是三个月前的旧镜像，跟我正在分析的 digest 毫无关系。后来查实：`stable` 就是 `0.27.3`，最新正式版，一直都是。

这个错误特别值得警惕，因为它**看起来很有解释力**——它能自洽地解释我看到的所有现象，还顺带产出了一条"深刻的洞察"。但解释力强不等于为真，尤其当你的观测本身是坏的时候。坏数据 + 强推理 = 一个精致的错误。

**第三次**：我查 ghcr 的 tag 列表，用 `tags/list?n=1000`，返回 `total: 1000`，我把它当成了全部。这个仓库实际有 1074 个 tag，registry 单页上限就是 1000。截断掉的部分里正好有全部正式版 tag，于是我看见的 0.27 全是 beta，得出"0.27 只有预发布"的结论，把服务端推到了一个没必要的 beta 上。

一个恰好等于整数上限的返回值，本身就该触发怀疑。我没有。

## 修了什么

**部署脚本加 `set -eo pipefail`**：

```rust
// A failed `build` used to fall straight through to `up -d`, which
// started whatever image was already on the host and returned 0.
"set -eo pipefail".to_string(),
```

`set -u` 没加——pre-deploy 钩子里引用了一些在某些主机上合法缺失的 `.env` 键，把那些变成硬失败是另一个决定，不该混在这次修复里。

改完立刻验证：同样的部署，现在 `exit=1`。

**删掉本地构建层和那个补丁**。0.27 已经把补丁做的事收编成了原生配置项，只剩一项安全加固还需要它——不值得为此维持一个匹配编译产物字节的脚本。compose 直接引用上游镜像。

**版本号从 `.env` 挪回 compose**，由 pin 工具统一管理，消除双重来源。

**修 pin 工具**：它原本只改 compose 不改 catalog，而 catalog 才是版本检查的数据源；它也匹配不了 `image@sha256:` 形式。顺带说，我修这个的第一版用正则从 key 惰性匹配到 `current_ref`，结果 rustfmt 把长 digest 折行后匹配跨过了条目边界，**把另一个镜像的 tag 改成了这个镜像的 digest，还报告成功**——又一次静默的错误行为，被我自己写的测试当场抓住了。这次测试救了我，是因为我特意让测试 fixture 按 rustfmt 的真实折行格式生成。

## 可复用的结论

**一、验证要回答"这次操作改变了什么"，不是"系统还活着"。**

我在上一篇里写过"要看运行事实，不看配置事实"，还挺得意。这次我查了 `/info`、查了 verify、查了 HTTP 200——全是运行事实，全是绿的，全都没用。因为它们回答的是"系统是否健康"，而我要问的是"我刚才那次部署有没有生效"。

对镜像部署来说，能回答后者的是这些：

```bash
docker image inspect <tag> --format '{{.Created}}'   # 构建时间是不是刚才
docker inspect <容器> --format '{{.Image}}'          # 容器用的是不是新镜像
docker exec <容器> cat /app/package.json             # 跑起来的东西自报什么版本
```

第一条最直接。一个应该刚构建的镜像，`Created` 显示三个月前，一秒钟就能定性。

**二、一个不改变任何东西的操作，必须失败。**

`docker compose build` 失败之后还去 `up -d`，本质上是"我没做成，但我假装做成了"。所有编排脚本都该默认 `set -e`；例外要显式写 `|| true`，并且写清楚为什么可以失败。

反过来检查你手头的部署工具：找一个必定失败的步骤，人为触发一次，看退出码是不是非零。这是十分钟的事，能验证你的整个反馈回路是不是通的。

**三、稳定复现的警告不是噪音。**

噪音的定义是随机、无信息。一条每次都出现、内容固定、指向具体行号的警告，是一个**你选择不修的问题**——它一直在那儿等着变成故障。

**四、恰好等于上限的返回值要怀疑。**

`total: 1000` 而分页上限就是 1000，`limit 100` 返回正好 100 条——这种数字几乎肯定意味着截断。分页写起来烦，但漏数据的代价是基于残缺集合做决策。

## 什么情况下这些不适用

- **托管平台的部署**（比如各种 PaaS）通常自己处理了失败传播，`set -e` 这条不用你操心，但"配置改了没生效"的问题会以别的形式出现（缓存的构建产物、未重启的实例）。
- **不可变部署**（每次都是全新镜像 + 全新实例）天然免疫"跑着旧镜像"这类问题——代价是重建成本。本文这套是给"原地 build + up"的 compose 部署用的。
- **只有一条配置来源**时，第一层那个陷阱不存在。会踩到它，是因为 compose 的 `${VAR:-default}` 天然支持覆盖，而覆盖是静默的。任何有分层配置的系统都值得问一句：我改的这一层，是不是被上面某一层压着？

## 一句话版本

部署报告成功不等于部署生效。让一个不改变任何东西的操作明确失败，比事后追查它为什么没生效便宜得多——我这次的代价是三个月，外加三次基于假证据的错误推理。
