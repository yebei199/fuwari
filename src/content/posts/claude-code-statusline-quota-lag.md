## 症状

Claude Code 的状态栏上有两个额度百分比：5 小时窗口和 7 天窗口。用久了会有一种挥之不去的感觉——**它显示的数总是比实际消耗少**。

这种"感觉型 bug"最容易走错第一步：直接去翻自己写的那段渲染代码，找一个能解释症状的可疑之处，改掉，然后宣布修好了。问题是这类症状往往横跨好几个自己没写的组件，改错地方不会报错，只会让你带着"已经修过了"的错觉继续用。

所以第一步不该是找 bug，而是**把链路切成段，逐段证明哪一段是新鲜的**。

## 一、先把链路钉死

这条状态栏的数据只有一条路：

```
服务端
 └─ 随某次 API 响应回传 rate_limits 快照
     └─ 客户端存在内存里
         └─ 每次渲染状态栏时，作为 stdin JSON 的一个字段喂给渲染器
             └─ 自己写的脚本读它、合并进本地共享缓存、渲染
```

自己能改的只有最后一段。于是要回答的问题变成：**最后这一段有没有引入滞后？**

三个互相独立的验证：

**1. 渲染器这端不缓存。** 翻它的 dist 产物，自定义命令 widget 的 `render` 是直接 `execSync` 起子进程，没有任何结果缓存层。也就是说状态栏每重画一次，脚本就真的跑一次。

**2. 脚本确实在跑，而且数在动。** 直接盯共享缓存文件的内容和 mtime。同一轮对话进行中，它从 `5h 4%` 变到 `6%` 再到 `53%`，mtime 一路跟着 `date` 走，差距在十几秒内。这一条直接否掉了"要等一轮对话结束才更新"的猜想。

**3. 本地没有第二份数据。** grep 会话 transcript 的 jsonl，`rate_limits` 一次都没被写进去（唯一命中是自己刚才敲的命令回显）。也就是说除了那个 stdin 字段，本地没有别的来源可以拿来对账，也没有一个"更新的副本"被忽略了。

三条合起来：**状态栏的新鲜度完全等于那个 stdin 字段的新鲜度，自己这段没有引入任何延迟。**

排查到这里，最有价值的产出其实是一个否定结论。它把后面所有的猜想都挡在了自己的代码之外。

## 二、途中捡到的真 bug：单调合并的缓存忘了过期

那个共享缓存是几天前为了解决另一个问题引入的——同一台机器上开多个会话，每个会话手里的快照新旧不一，各显各的就会互相打架，那次的过程写在[前一篇](/posts/statusline-quota-pace-shared-cache/)里。合并规则很自然：

- `resets_at` 更晚的窗口，整体替换（说明窗口翻篇了）；
- 同一个窗口内，取 `used_percentage` 较大者（窗口内用量单调不减）。

看着没毛病，实际漏了一种情况：**窗口已经重置，但本机还没收到任何新快照。**

这时缓存里躺着的是上一个窗口的高百分比，`resets_at` 已经是过去时间。倒计时那一项被 clamp 成 0，于是状态栏渲染出：

```
5h 87%(-13) ↺0m
```

87% 是上一个窗口的账，此刻真实用量接近 0。这个数不只是陈旧，**它错的方向还是让人安心的那个方向**——你以为快到墙了，其实刚开局；反过来的场景（新窗口已经烧掉一半，显示还停在上个窗口的低值）同样成立。

根因一句话：**单调合并的缓存，如果没有过期规则，就会在源头静默期间无限期地保留最后一个值。** 合并规则本身没错，错在它假设"总会有新数据来纠正"。

修法也是一句话——合并之后，把 `resets_at` 已经过去的桶直接丢掉，让整段消失，等下一份快照重新播种。宁可不显示，也不显示一个错的。

### 验证方式：把逻辑抠出来单跑

这段逻辑写在 jq 里，而 jq 又嵌在配置语言的多行字符串里，外面还套着 shell。整条链路要重新部署一次才生效——这就意味着"改完跑一下看看"的循环长达好几分钟。

省时间的办法是**把纯逻辑抠出来单独跑**。用 `sed` 从配置文件里把那段 jq 程序原样抽到一个临时文件，然后直接喂构造好的输入：

- 旧缓存已过期 + 没有新快照 → 应当什么都不渲染；
- 旧缓存未过期 → 照常渲染；
- 旧缓存已过期 + 有新快照 → 用新快照重新播种。

三种都当场验过，再去改测试、走部署。这里的关键不是 `sed` 这个技巧，而是**认出"纯函数"的边界**：这段 jq 不读文件、不发请求，输入全在参数里，那它就可以脱离整条链路单独验证。嵌得再深的逻辑，只要是纯的，就不该用完整部署去验。

至于自检用例，它跑的是磁盘上已部署的脚本，所以写完先是红的，红的内容恰好把症状原样打了出来——这比"测试通过"更让人放心，因为它证明这条断言真的在测那件事。部署之后转绿。

## 三、剩下的滞后：两个来源，都不在本地

自己这段既然是干净的，剩下的滞后就有了明确归属。

### 来源一：采样保持

那个字段只在**有 API 响应到达**时才被换成新值。两次响应之间，它是冻住的。

这听起来无害——不发请求就不消耗嘛。但它有一个方向固定的后果：

> 一轮对话的最后一次请求，它自己的开销永远不在显示的数字里。

因为那次请求的成本要等**下一次**响应才报得出来。而一轮对话的最后一次请求，通常是上下文最长、最贵的那次。

更关键的是这个缺口**在空闲期间不会自愈**。停下来一小时，状态栏就整整一小时挂着偏低的数。回来发第一条消息，响应一到，数字"咣"地跳上去——看起来像是刚才那一句吃了 8%，其实是把一小时前欠的账一次性补上。

这大概就是"总是落后"这个感觉的主要来源：**看到的永远是上一次响应到达那一刻服务端记的账，不是此刻的账。**

（有一点我没能验证：服务端算这个快照时，算不算正在处理的这次请求本身。倾向于不算——限流检查通常发生在受理请求之前——但没有实测支撑，标为推测。无论哪种，结论不变。）

### 来源二：账号级的桶，只有一部分消费者会喂本地缓存

这两个额度桶是**账号级**的，不是某台机器或某个会话的。而下面这些都在吃同一份额度，却从不渲染这条状态栏，因此永远不会往本地缓存里写一个字：

- 无头模式运行的实例（包括各种脚本、钩子里调起来的）
- 云端定时任务
- 另一台机器上的会话
- 网页版、桌面 App
- 任何其他登同一账号的客户端

好消息是这一条**不会累积成永久误差**：本机一有响应，服务端给的就是全账号的最新总数，一次补齐。它是延迟，不是漂移。

## 四、反直觉的部分：换"实时"数据源反而更粗

确实存在一个更权威的数据源：一个内部 usage 端点，需要拿本地凭据文件里的 OAuth token 去调。状态栏渲染器本身就带这条回退路径——布局里只要出现任何一个官方快照供不出数的 widget，它就会自动启用。

看起来是个干脆的解法。但翻它的实现会看到一个决定性的细节：**这条路径自己有 180 秒缓存。**

于是它给的不是实时，是"最多落后 3 分钟"。两条路对比：

| 场景 | 当前（响应快照） | 换成 OAuth 取数 |
|---|---|---|
| 正在连轴干活 | 每收到一次响应就更新，一分钟好几次 | 每 180 秒一次 |
| 空闲 | 冻住不动 | 每 180 秒一次（但也没在消耗） |
| 别处在吃额度 | 看不见，直到本机下次响应 | 能看见 |

**在最关心额度的那个时刻——正在连轴跑任务的时候——现在这条路更新得更勤。** 前面那半小时里从 6% 跳到 53%，状态栏是一路跟着动的，换成 3 分钟一采样只会更粗。

OAuth 路径真正赢的只有一种场景：经常在别处并行吃额度、而这台机器闲着。不是常态的话，这笔交易换来的几乎只有"空闲时数字也动"。

代价那边还有一条更实的：这个包是**不钉版本**装的，而刷新定时器是**每小时**跑一次。也就是说它的代码每小时自动换一次，无人复核。现在它没有任何理由去碰凭据文件；一旦启用那个 widget，"读取 OAuth token 并向外发请求"就变成它的**常驻行为**。

未文档化的端点 + 自动更新的第三方代码 + 常驻凭据访问，三个里任意两个都还能接受，三个凑齐就不值了——尤其是为了换一个"空闲时数字也动"。

需要精确数字的时候，直接跑客户端自带的 `/usage`：同一个数据源，按需、一次性、没有常驻成本。一天真正需要精确对账的次数是个位数，为此让状态栏每 3 分钟发一次请求，比例不对。

## 可复用的结论

1. **面对"感觉型"症状，先证明自己那段是新鲜的，而不是先找 bug。** 一个否定结论（"延迟不在这里"）能把后续所有猜想挡在门外，比一个可疑的修改值钱得多。
2. **单调合并的缓存必须配过期规则。** 合并规则保证"不会倒退"，但同时也保证了"源头静默时最后一个值会永远留着"。这两件事是同一个性质的两面。
3. **数据错的方向比错的幅度更重要。** 一个让人安心方向的错数，比没有数字更危险，因为它会阻止你去查。
4. **评估"更实时的数据源"时，先问它自己的采样周期。** 一个 180 秒轮询的"实时 API"，可能比一个跟着事件走的"陈旧快照"更粗。名字里的"实时"不是性质。
5. **嵌套再深的纯逻辑，也该脱离完整链路单独验证。** 判据是它读不读外部状态，不是它写在哪一层字符串里。
6. **把推测标成推测。** 排查报告里"我没验证这一点"是有价值的信息，把它写成事实才是损失。
