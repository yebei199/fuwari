起点是一个听起来只需要回答「能」或「不能」的问题：

> AFFiNE 服务端开 indexer（要额外跑 Elasticsearch 或 Manticore），当前我的可以开启吗？

机器是一台 16 GB 内存、10 核的 aarch64 VPS，当时还剩 8.1 GB 可用。所以答案是能。但这个答案没什么价值——真正要定的是开哪个引擎，而这件事的分歧点，跟内存关系不大。

## 分歧点在分词，不在内存

第一反应是从资源出发：Elasticsearch 的 JVM heap 默认吃掉容器内存的一半，实际要 2 GB 起；Manticore 常驻低几百 MB。加上这台机器 **swap 是 0**，OOM 就是直接杀容器，没有缓冲。看起来 Manticore 赢了。

但这个理由其实是最弱的一条。8.1 GB 可用，ES 的 2 GB 并不致命，只是难看。

去翻上游源码之后，真正的差距出现在中文分词上，而且方向和我预期的相反——我本以为这会是 ES 翻盘的地方（生态成熟，ik、smartcn 随便挑）。结果两边都不需要装插件，因为 AFFiNE 刻意避开了插件依赖：

- **Elasticsearch** 用内置的 `cjk_bigram` 过滤器，双字加单字切分。「我是地球人」切成 `我 / 我是 / 是 / 是地 / 地 / 地球 / 球 / 球人 / 人`。能搜，但没有词边界概念，召回够、精度差。
- **Manticore** 用 `morphology = jieba_chinese`，真词典分词，`manticore-language-packs` 已经装在官方镜像里。

也就是说，AFFiNE 在 ES 路径上选 bigram 不是因为它更好，是因为它不用装插件。对中文文档来说，这个妥协的代价直接落在搜索质量上。

**如果这是个英文库，这一整段理由都不成立。** 选型结论不可移植，能移植的只有「先去看它怎么分词，再看它吃多少内存」这个顺序。

## 「支持两种 provider」是不对称的

代码里确实两种都在。但翻一遍就会发现它们不是一个量级的东西：

| | Manticore | Elasticsearch |
|---|---|---|
| 默认 provider | 是 | 否 |
| 自托管文档 | 唯一被记录的路径 | 从未提及 |
| CI 覆盖 | 跑完整 server 测试套件 | 只跑几个 provider 单测 |

最有信息量的是 CI 那一行。文档可以只是没写，但 CI 跑什么不会撒谎：**一条路径只跑了 provider 层的单测，就意味着没有人验证过它端到端能用。**

有意思的是，代码结构和这个结论是反的——`ManticoresearchProvider extends ElasticsearchProvider`，ES 才是基类，Manticore 是子类。继承关系告诉你谁更「基础」，CI 配置告诉你谁更可靠，这两个信号指向相反的方向。信 CI。

而且那个接缝确实是漏的。上游 issue #13559：`hits.total` 在 ES 侧是 `{value: number}`、Manticore 侧是 `number`，ES 的形状漏到 GraphQL 的 `Int` 字段就报错。**选了默认路径，不等于选了没有 bug 的路径**，只是选了 bug 会被更多人踩到、因而更可能被修的那条。

## 关闭的 issue 不等于修复的 issue

这条是这次最值钱的发现。

上游 issue #13929：indexer 开着但 Manticore 连不上时，数据迁移直接崩，整个栈起不来。这个 issue **已经关闭**，时间在我们跑的版本发布之前。

正常的推理是：关闭了，发布在其之后，所以修了。

实际去读那个版本的代码，失败路径原样还在：

- `createTables()` 只 catch 了「provider 未配置」，没 catch「provider 连不上」；
- provider 用的是裸 `fetch()`，`ECONNREFUSED` 直接冒成 `TypeError: fetch failed`；
- 迁移 runner 接住之后 `process.exit(1)`；
- 迁移容器非零退出 → 主服务的 `service_completed_successfully` 不满足 → **整个栈起不来**。

那个 issue 关闭时**没有关联任何 commit 或 PR**。它是被关掉的，不是被修掉的。上游给的实际缓解手段藏在文档里的 compose 片段中——给迁移容器加 `depends_on: condition: service_healthy`。文档不会告诉你这行是防什么的，只有把 issue 和代码对上才知道它是唯一的护栏，不能删。

**教训：issue 状态是社交信号，不是技术事实。** 要确认一个 bug 修没修，只能去读你实际要跑的那个 tag 的代码。

## 开一个「可选功能」，买下一个永久依赖

建索引表的那个迁移声明了 `always = true`，意思是**每次部署都重跑**，不是只跑一次。

把这个和上一节拼起来，结论就变了：Manticore 挂掉不只是「搜索用不了」，而是**任何一次部署都会失败**。一个原本可选的搜索功能，一旦打开，就变成了主服务的启动硬依赖，而且是永久的。

这不是可以绕开的实现细节，是启用它的既定成本。值得在决定开之前就说出口，而不是半年后某次部署挂了才发现。

## 环境变量只是默认值

另一个坑，代价是回滚能力：

管理后台写的是数据库配置，**优先级高于环境变量**——环境变量只提供默认值。一旦从 UI 打开过 indexer，改 compose 里的 `false` 就再也关不掉了，只能去数据库删行。

所以这次的处理是：**只从 compose 的环境变量开关，永远不碰管理后台**，并且在两处配置旁边写死注释说明原因。只走环境变量时回滚是干净的——provider 不注册 → 抛「未找到」→ 建表提前返回 → 迁移通过。

这类坑的共性是：**一个看起来等价的操作入口，实际上有不同的持久化层级和不同的不可逆性。** UI 上的那个开关和 YAML 里的那一行，看着在做同一件事，实际上一个是写数据库、一个是给默认值。

## 一个静默失败的标志位

回填是自动的：一个 30 秒一轮的 cron 扫工作区、把存量文档补进索引，不需要手工触发。这是选 Manticore 之后省下的一整块工作。

但它的第一行是这样的：

```
if (workspace.indexed) continue;
```

这个 `continue` **发生在比对真实索引之前**。也就是说：如果哪天清空了索引 volume，而数据库里的 `indexed` 标志还是 `true`，那些工作区就永远不会重建索引——除非有人恰好去编辑它。

症状是「搜索悄悄搜不到旧文档」，零报错，零日志。

**标志位和它声称的状态解耦，失败就是静默的。** 这次没有为它写自动检测（「volume 是空的」这个判定本身很脆），而是把它写进了运维文档：删 volume 之前先重置标志。这是个权衡，不是完美方案——赌的是下次踩到时有人会去翻文档。

## 所有检查都绿，但没有一个证明它能用

部署完之后：数据迁移过了、容器在跑、环境变量断言通过、主服务的 HTTP 探针可达、公网 200。全绿。

但这里面没有一条证明**搜索能搜出东西**——而这是整件事唯一的目的。

自动化够不到这一层是有具体原因的，不是偷懒：索引引擎的端口按上游设计不发布到宿主（只有同栈服务需要它），而部署工具的 HTTP 探针是在宿主上跑 `curl` 的，够不着容器网络。所以能自动断言的上限就是「容器活着」。

最后是靠 AFFiNE 自己的 MCP 接口做的端到端验证——`keyword_search` 走的正是索引那条路径：

| 查询 | 首条命中 |
|---|---|
| 部署 | 本地部署模型 |
| 服务器 | 一个printf调用实现Web服务器 |

两个结论：中文命中相关，jieba 按预期工作；结果里出现了两个月前创建的旧文档，说明回填 cron 已经把存量爬完了，上一节那个标志位地雷这次没踩到。

需要如实说的边界：**排序质量只能判断「不离谱」，没有做召回率或精度的量化对比。** 说 jieba 比 bigram 好，依据是分词原理和上游代码，不是我在这个库上实测出来的数字。

## 留下的东西

真正可复用的不是「选 Manticore」这个结论——那高度依赖于「中文」和「这台机器 swap 是 0」。可复用的是几个提问顺序：

- 先问它怎么分词，再问它吃多少内存。**资源是最容易量化的维度，所以最容易被当成决策依据，哪怕它排在最后。**
- 想知道一条代码路径可不可靠，去看 CI 跑什么，别看它有没有被实现。
- issue 关闭了不代表修了。去读你要跑的那个 tag。
- 开一个可选功能之前，先算清楚它会不会变成不可选的依赖。
- 部署全绿和功能可用是两件事。想清楚哪些断言是自动化够不到的，然后老老实实手工补上那一刀。
