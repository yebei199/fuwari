图片终于能在手机上显示之后,冒出来一个新问题:**点图片没有任何反应。**放大不了,也找不到下载入口。桌面端点一下就会弹出全屏预览。

翻到那个块的实现,答案在文件开头:

```ts
@Peekable({
  enableOn: () => !IS_MOBILE,
})
export class ImageBlockComponent extends CaptionedBlockComponent<ImageBlockModel> {
```

移动端整个不启用点击预览。**没有注释。**引入这行的提交也追不回来——它来自上游把编辑器合并进主仓库之前的时代,那次合并把历史压成了一个 `chore: merge ... source code`,理由随着提交信息一起没了。

所以「为什么不做」只能从代码本身推断。下面把我查到的事实和我的推断分开写。

## 事实:那个预览器是个纯桌面器件

被拦住的这个预览界面,缩放逻辑集中在一个 hook 里。读完它的输入方式,整套是鼠标语汇:

- 缩放靠界面上的放大、缩小、重置三个按钮,以及滚轮;
- 平移靠 `draggable` 加鼠标拖拽,状态变量叫 `dragBeforeX` / `dragBeforeY` / `isDragging`;
- 关闭靠在 `document` 上监听 `keydown`,判断 `Escape`;
- 里面甚至有 `image.style.cursor = 'pointer'` 这种只对有光标的设备才有意义的代码。

整个文件里**没有一处 touch 或 pointer 事件**。没有捏合缩放,没有双击缩放,没有下滑关闭。

也就是说,在触屏上,这个模态框唯一还能用的是那三个小按钮,而**关闭手势是缺失的**——手机上按不出 Escape。打开它,然后困在里面。

## 事实:同一个装饰器的另外两处判断,形状不一样

这个 `@Peekable` 装饰器在别的块上也用,`enableOn` 一共出现三次:

- 附件块:判断这个附件的**类型**能不能预览;
- 画布引用块:判断它**有没有**引用到一个真实对象;
- 图片块:判断**当前设备**是不是移动端。

前两处是能力判断——这个对象本身能不能被预览。只有图片这处是设备判断。

这个差别很说明问题:它拦下的不是「这个东西不能预览」,而是「**这个设备上还没有能用的预览器**」。前者是产品语义,后者是施工状态。

## 事实:移动端是重写,不是缩放

整个编辑器里有六十多处按 `IS_MOBILE` 分叉的代码,代码块、数据库块、表格、右键菜单都在其中;而移动端界面本身是一个和桌面端并列的独立目录,不是同一套组件加几条媒体查询。

这说明上游对移动端的态度是**重新实现**,不是让桌面组件自适应。在这种架构下,一个还没被重写到的桌面组件,默认状态就应该是关掉,而不是勉强复用。

## 推断:宁可不给入口,也不给一个关不掉的模态框

把上面三条放在一起,我的推断是:上游知道桌面预览器直接搬到触屏上会得到什么——缩放别扭、关闭困难的模态框——于是先把入口关掉,等移动端重写到这里再打开。

这是标注为推断的部分,代码里没有任何一句话这么说。但我认为这个判断是对的:一个打得开、关不掉的预览,比没有预览更糟。用户点不开还能去桌面端看,被困在模态框里只能杀进程。

## 它至今没排上,而不是被否决

顺手查了最新的开发分支:那行开关到今天一字未改,图片块整个目录相对上一个稳定版本**零改动**。同期移动端确实在开发,近三个月大约一千八百行改动,新增了列表空状态、原生用户标识之类的东西——但**没有一行涉及图片预览**。

这就是典型的「有替代路径、不阻塞核心流程」的功能:文档能读、图片能显示,看不清可以去桌面端。而同步、登录、列表是每天每次都要走的路径。优先级排下去了,不是被否决了。

对我这种自建者来说,这个查证很有价值:它意味着**升级到最新版本不会带来任何改善**。如果不查,很容易默认「那就等下个版本吧」,然后无限期地等一个没人在做的东西。

## 更一般的一条:判断的形状本身是证据

读没有注释的代码时,我们习惯问「这个条件在判断什么」,但更有信息量的问题是「**这个条件是哪一类判断**」。

- 能力判断(这个对象支持吗)通常是**产品语义**,大概率会长期存在;
- 设备判断、平台判断、环境判断,尤其是当它孤零零地混在一堆能力判断里时,通常是**施工状态**——意思是「这里还没做」,不是「这里不该有」。

这个区分能直接改变你的决策:前者你应该接受并绕开,后者你可以自己补上,或者去上游催。这次的情况属于后者,一行改动就能打开开关。代价是你会拿到上游选择不发的那个东西——所以真要开,得连带补一个可用的关闭方式,否则就是把上游避开的那个坑自己踩一遍。
