这个故障没有报障人。没人抱怨,没有告警,监控全绿,服务日志里也只是多了几行 WARN。我是在排查另一个完全无关的问题时,扫日志顺手看到的。

等查完才发现:全文搜索的索引已经停更了三天,期间**每一次**写入都失败。

## 它为什么不会被发现

派生数据的故障和主数据的故障,失败形态完全不同。

主数据坏了,服务立刻不可用,你马上就知道。而搜索索引是**派生数据**——它坏了以后,系统并不会停下来,它会继续拿上一次成功的结果为你服务。你搜东西,有结果返回,结果看起来也对(它们确实曾经是对的),只是新东西再也搜不到了。

这种「用过期数据伪装成正常」的形态,缓存、物化视图、embedding、搜索索引全都有。它不会触发任何可用性监控,因为服务一直是可用的。

## 第一个误判:只数了分子

发现告警后,我先看了当天的日志,得出结论「409 只涉及 1 篇文档」,于是判断影响面很小,建议先不动。

这个判断被一句话推翻了:「如果是 bug,不该只影响一篇文章。」

对。我数了分子,没数分母。重新查:

- 7 天内被推送索引的文档:**3 篇**
- 其中失败的:**3 篇**

100% 失败率。当天只看到一篇,纯粹因为当天只编辑了一篇。同样的日志,数分子得到「偶发」,数分母得到「全坏」——而这两个结论对应的处置完全不同:偶发可以观察,全坏必须立刻修。

**看失败日志时,先找分母。** 失败次数本身几乎不含信息量,失败率才有。

## 根因:CREATE TABLE IF NOT EXISTS

索引里最新的一条记录停在三天前的下午两点。而前一天下午,服务端刚部署过。

那次部署在提交信息里被归类为「同 tag digest 重推」——看起来只是上游重新构建了一次同一个版本。实际上它把服务端从 0.27.3 带到了 0.27.4。这是 digest 锁定的一个副作用:你锁的是内容哈希,上游把 `stable` 这个 tag 指向新版本时,你看到的只是一串哈希变了,看不到版本号跳了一位。

新版本给索引表加了 7 个列(`unit_id`、`projection_version`、`source_hash`、`visibility`、`element_id`、`frame_id`、`source_block_id`)。而建表语句是:

```sql
CREATE TABLE IF NOT EXISTS block (...)
```

这条语句在一个**每次部署都会执行**的迁移里(标着 `always = true`)。所以从表面看,它每次部署都会把表结构对齐一次,非常安全。

但表已经存在了。`IF NOT EXISTS` 让它变成一条空操作,旧表结构原样保留。新版服务端往里写带 `unit_id` 的数据,搜索引擎回:

```
"type": "mapper_parsing_exception",
"reason": "unknown column: 'unit_id'"
```

全新安装的实例完全不受影响,因为它建表时就是新结构。**只有升级上来的实例会中招**——这也是它至今没人报的原因:开发者本地一跑就是新装,永远复现不出来。

## 第二层:自愈机制被一个游标废掉了

这类问题上游其实有解:代码里有一个 `rebuildManticoreIndexes()`,删表重建再全量回填;数据库里有一个 `indexed` 布尔标记,把它置为 `false`,后台任务就会重新索引整个 workspace。半年前另一次表结构变更,上游就配套发过一个一次性迁移来调它。这次加 7 个列,忘了配。

于是我手动走这条路:补上缺失的列,把 `indexed` 置为 `false`,等后台任务回填。

**结果什么也没发生。**

去读那个后台任务才明白:它按 `sid > 游标` 分页扫描 workspace,每轮把游标推到本轮最后一个 sid,然后重新入队自己。游标只进不退。一旦它扫过了你的 workspace,你再把 `indexed` 重置成 `false`,它也永远不会回头看一眼。定时器每 30 秒确实会尝试塞一个新任务,但会被同名任务去重挡掉。

在 Redis 里能直接看到这个卡住的状态:

```json
{"payload":{"lastIndexedWorkspaceSid":1}}
```

而唯一的 workspace 的 sid 不大于 1,于是 `sid > 游标` 这个窗口永远是空的。

**官方的恢复机制,在官方的调度器里是死的。** 这一层比第一层更值得记:第一层是忘了写迁移,是疏忽;第二层是两个设计各自都合理(单调游标用来增量发现新 workspace,重置标记用来触发重建),组合起来互相抵消。

最后能触发重建,靠的是另一条完全不同的路径:任何一次文档编辑都会直接为整个 workspace 排一个索引任务,不经过那个游标。也就是说,修复这个故障的最后一步,是在编辑器里随便敲一个字。

## 修复与验证

三步:

1. 给索引表补上缺的 7 个列(`ALTER TABLE ... ADD COLUMN`),与新版建表语句对齐。加列是纯增量操作,已有数据原样保留;而且当时写入本来就全部失败,不存在打断写入的问题。
2. 把 workspace 的 `indexed` 标记置为 `false`。
3. 在任意文档里编辑一下,触发那条绕开游标的路径。

不需要重启,不需要重新部署。验证四项:

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 搜索特定关键词 | 0 命中 | 3 个块命中 |
| 索引最新写入时间 | 冻结在 3 天前 | 当前时刻 |
| 409 告警 | 每次编辑必报 | 5 分钟内 0 条 |
| `indexed` 标记 | 手动置 false | 自动回到 true |

最后一项是最有说服力的:标记是回填任务自己跑完之后设回去的。它变成 `true`,说明整条链路真的走通了,而不是我手动改出来的假象。

## 真正的教训:幂等不等于收敛

`CREATE TABLE IF NOT EXISTS` 是**幂等**的——跑一次和跑一百次结果一样,不会报错,不会重复建表。所以它看起来非常适合放在一个「每次部署都执行」的迁移里。

但幂等不等于**收敛**。收敛的意思是:不管当前状态是什么,执行之后都会到达目标状态。`IF NOT EXISTS` 只保证「表存在」,不保证「表是对的」。当目标状态从「有这张表」变成「有这张表且有这些列」时,它就不再收敛了——它会安静地停在一个错误的状态上,而且因为它不报错,看起来像成功了。

这是所有声明式配置工具的老问题:`CREATE ... IF NOT EXISTS`、`mkdir -p`、`INSERT ... ON CONFLICT DO NOTHING`,都属于「存在即跳过」。它们在**创建**语义下是对的,在**收敛**语义下是错的。而升级路径要的永远是后者。

判断方法很简单:问自己「如果目标结构变了,这条语句会把已有的旧结构改过来吗?」答案是「不会,它只是跳过」的话,那你就还欠一条迁移。

其余几条:

- **派生数据要监控新鲜度,不是可用性。** 索引、缓存、物化视图坏掉时都会继续提供服务,只是数据是旧的。一条「最新写入时间距今超过 N 小时就告警」的检查,能在三天前就抓到这次故障。可用性监控永远抓不到。
- **数分母。** 失败次数在「偶发」和「全坏」两种情况下长得一模一样,失败率才能区分它们。
- **自愈机制没验证过就不算存在。** 代码里有一个重建函数、数据库里有一个标记位,不代表这条路是通的。这次的两个组件都在,链路却是断的。

## 什么情况下这套判断不适用

- **全新安装的实例**:这个坑根本不存在,建表时就是新结构。反过来说,只在全新环境里验证过的升级,不算验证过升级。
- **失败是部分而非全部**:那更可能是数据本身的问题(某些内容触发边界条件),而不是结构不匹配。结构不匹配的特征是 100%。
- **上游已经重构掉的版本**:这个项目在我修完的当天早上,恰好往开发分支合了一个重构,给索引表引入了结构指纹机制——结构变了就自动开新一代表并迁移。这类「改了 schema 忘了迁移」的问题从此在架构上消失了。所以如果你跑的是更新的版本,这篇的根因部分对你不成立,但「幂等不等于收敛」那条依然成立。
